# shovel 設計決定ログ

設計議論で確定した事項を記録する。各項目は「決定 / 理由 / 影響」で構成する。
未決の論点は `docs/design/open-issues.md` を参照。

---

## A-1. ACP クライアントは公式 TypeScript SDK を直接使う

**決定**

- `@agentclientprotocol/sdk`（公式 TypeScript SDK, Apache-2.0）を直接利用する。
- **Vercel AI SDK は採用しない。** 要求書の「Vercel AI SDK (ACP)」の記載は削除する。
- `@ai-sdk/harness-acp`（公式 ACP ハーネス）も `@mcpc-tech/acp-ai-provider`
  （コミュニティプロバイダ）も採用しない。

**理由**

1. **接続方式が合わない。** `@ai-sdk/harness-acp` はサンドボックス内にブリッジ
   プロセスを置き WebSocket で通信する方式で、**ポート公開が必須**。
   Docker Sandboxes でのポート公開はホスト側での `sbx ports --publish` 実行を
   要し、非エンジニア向けアプリの前提と両立しない。
   `sbx exec -i <name> <agent>` の **stdio 直結**の方が単純かつ確実。
2. **対話的承認ができない。** ハーネス層の権限モデルは
   `allow-reads` / `allow-edits` / `allow-all` の静的ポリシー。
   `session/request_permission` の `options` から選択肢を生成し、Diff を見せて
   都度承認させる UI は表現できない。
3. **セッション履歴 API が無い。** ハーネス層は `createSession` / `detach` /
   `stop` / `destroy` のみ。要求書の中核である `session/list`（一覧）と
   `session/load`（アプリ外セッションの復元）に相当する API が存在しない。
4. **表示情報が落ちる。** `agent_thought_chunk` / `plan` /
   `tool_call` の `kind`・`locations`・`diffs` / `switch_mode` /
   `available_commands` / `usage_update` が失われ、UI 仕様の大半が
   実装できなくなる。
5. **Vercel 自身が次善策と位置づけている。** ACP メタアダプタは direct adapter が
   存在しないハーネスのための救済策であり、「ACP の抽象は内部挙動の露出を
   制限しうる」と明記されている。

根底にある理由: **AI SDK のハーネス層はエージェントをバックエンド部品として
隠蔽するための抽象であり、shovel はエージェントの挙動そのものをユーザーに
見せて操作させるアプリである。抽象の方向が逆。**

**この決定が覆る条件**

対話的承認が不要（サンドボックス隔離のみを安全境界とする）かつセッション履歴の
復元が不要になった場合に限り再検討の価値がある。ただしポート公開問題は残る。

**影響**

- ACP クライアントは SDK を使うため自作不要。
- ただし次のレジリエンス対策は SDK の上に自前で載せる必要がある
  （capability は `true` / `{}` の双方を真として扱う、タイムスタンプは
  epoch ms / epoch 秒 / ISO-8601 を正規化、未知バリアントはログして無視、
  `stdout` のみ ACP パーサへ・`stderr` は分離、`initialize` は締切ではなく
  **アイドルタイムアウト**で判定）。
- チャット UI は shadcn/ui で構築する。AI SDK の UI 部品には依存しない。

## A-1b. ACP プロトコルは v1 のみをサポートする

**決定**

- `protocolVersion: 1` のみをサポートする。experimental な v2 は採用しない。
- ただし SDK の直接利用を UI 層に露出させず、**薄い抽象化層を挟む**。
  将来の v2 移行をその層の差し替えで完結させる。

**理由**

- ACP レジストリが配布するアダプタ（`@agentclientprotocol/claude-agent-acp` 等）が v1。
- v2 は experimental であり、本番採用の段階にない。

## C-4. プロジェクト非依存の「壁打ち」も ACP 経由で行う

**決定**

- 「プロジェクトに関係なく AI と壁打ち」は、**スクラッチ用サンドボックスを 1 つ用意し、
  通常のプロジェクトと同じ ACP 経路で会話する**方式とする。
- ホストから LLM API を直接叩く経路は設けない。

**理由**

- チャット UI が 1 系統に統一される。
- 認証情報の置き場がサンドボックス内に一本化される
  （ホスト側に API キー管理が発生しない）。
- エージェントの能力（検索・思考・ツール実行）をそのまま利用できる。

**影響**

- スクラッチ用サンドボックスの生成タイミングとワークスペースの位置は
  論点 N-2（サンドボックスのライフサイクル管理）で決定する。

## N-1. トランスクリプトは React で実装する

**決定**

- `TranscriptEvent` / `TranscriptAction` を **main ⇔ renderer の IPC 契約**として使う。
- ACP → イベントへの変換ロジック（`TranscriptToolCall` 等）は main 側に TypeScript で実装する。
- 描画・状態管理は React で実装する。
- Markdown は `react-markdown` + `remark-gfm`、シンタックスハイライトは `shiki` を使う。
- トランスクリプト内検索は Electron の仕組みを使う（下記）。

**理由**

1. **React では「id でパッチする」設計が不要になる。** イベントプロトコルが
   `id` を運ぶのは「DOM を作り直すと折り畳み状態とスクロール位置が飛ぶ」ため
   であり、React は仮想 DOM でこれを自動的に解決する。
2. **スタックの二重化を避ける。** shovel は Markdown エディタ・
   ファイラー・Diff ビューアなどトランスクリプト以外の UI も大量に作るため、
   単一スタックであることの価値が大きい。

**プロセス境界の対応**

```
main(Node)  ──イベントJSON──▶ renderer(React)
            ◀──アクションJSON──
```

ACP クライアントは子プロセス（`sbx exec`）を起動するため main で動かすしかなく、
UI は renderer。両者は IPC でしか通信できない。イベント語彙は
**ACP の生イベントを UI が扱える形に翻訳した中間表現**であり、描画技術とは独立している。

**必ず守る挙動（ライブラリでは解決されない）**

- **リンクでウィンドウ内を遷移させない。** 相対パス `[ToDo](docs/ToDo.md)` を
  素のリンクにすると `file://` を踏んで壊れる。当初は「href を落とす」実装だったが、
  空の `href` のクリックは現在のページの再読み込みになり、ウィンドウの状態が
  失われた（2026-10-01 修正）。現在の規則: `http(s)` / `mailto` だけを外部で開き、
  プロジェクト内の相対パスはファイラーと同じくアプリ内で開く（行番号 `:12` は
  落とす）。`file://`・絶対パス・未知のスキームはリンクにせず文字として見せる。
  main 側でも `will-navigate` / `setWindowOpenHandler` で遷移をすべて止め、外へ
  渡すのは `http(s)` / `mailto` だけにする（開発時の同じページの再読み込みのみ許可）。
- **ストリーミング中はプレーンテキスト、ブロック確定後に Markdown 描画。**
  不完全な Markdown を描画すると表示が暴れる。
- **追記時のスクロール追従は「すでに最下部にいたときだけ」**（閾値 24px）。
- **折り畳み時はクリックした行を画面上の位置に保つ**
  （`getBoundingClientRect` の差分で `scrollTop` を補正）。
- **送信時はまず最下部へスクロール**してから応答を待つ。
- **ツールコールの行は折り返さない。** 溢れた分は省略記号で切り、全文は
  tooltip に置く（折り返すとアイコンが独立行に押し出され、静かなログが
  文字の壁になる）。
- **思考ログはチャットに流さない。** 入力欄の上の専用エリアに直近数行だけ表示し、
  ターン終了時に折り畳んで下に格納する。
- **ツールコールはグループに畳む。** 実行中 `Working… 12s` / 終了後 `Worked 12s`。
- **コピーの確認はトーストで行う。** クリップボードを持つのは main プロセス側
  なので、実際に書き込めたことを知っているのも main だけ。
- コードブロックのコピーボタンは `pre` の**外側のラッパー**に置く
  （`pre` は横スクロールするため）。

**セキュリティ（Electron での読み替え）**

- `react-markdown` は `rehype-raw` を入れない限り Markdown 中の生 HTML を
  一切通さないため、HTML サニタイズの問題が**構造的に発生しなくなる**。
  （例外: Markdown ファイルの表示に限り `<details>` / `<summary>` だけを要素にする。D-5 追記）
- ナビゲーション禁止は Electron の `will-navigate` と `setWindowOpenHandler`
  で塞ぐ。リンクは外部ブラウザへ。
- renderer は `contextIsolation: true` / `nodeIntegration: false` を前提とする。

**サブ論点: N-1-a 検索の実装方式**

TreeWalker で `<mark>` を挿入する方式は React の管理外 DOM 操作であり、
再レンダリングで壊れるため使えない。

- (a) Electron の `webContents.findInPage()` を使う
  → 自前実装が不要になる。ただし renderer 全体が対象なので
    サイドバーや入力欄もヒットする。
- (b) React のレンダリングに織り込む
  → ブロックのテキストを state から検索し、ハイライトを描画時に挿入する。
- (c) TreeWalker でテキストノードを集めて `Range` を作り、**CSS Custom Highlight API**
  （`CSS.highlights`）で塗る → DOM を書き換えないので React と衝突しない。

**決定（2026-10-06）: (c)。** いったん (a) で決めた（V-5）が、実装して動かすと
「検索バーの入力欄自身の文字がヒットに数えられる（3件が4件になり、次へ送ると入力欄に止まる）」
「`findInPage()` がヒット箇所を選択して入力欄のフォーカスを奪い、Enter で次へ進めない」
という、サイドバーへの誤ヒットより重い問題が出た。(a) のまま避けるには検索バーを別の
webContents に分ける必要があり重い。(c) は依存追加なしで両方を避けられ、対象をタブ領域に
絞れる（サイドバーの誤ヒットも消える）。代わりに textarea / input の中身は探せない
（Markdown エディタは右のプレビュー側でヒットする）。(b) は描画経路が多く（Markdown・shiki・
差分・ファイルビューア）織り込む箇所が散るため採らない。

**追記（2026-10-17）**: 編集面を CodeMirror 6 にした（N-3-1「改訂（2026-10-17）」）のに合わせ、
CodeMirror の中身も対象外にする。ソース・分割・「編集」のファイルのタブでは Cmd/Ctrl+F を CodeMirror の
検索パネルに任せ、チャットの横のエディタではフォーカスで分ける（分担の表は N-3-1 の同節）。

## D-5. Markdown レンダリングとシンタックスハイライト

**決定**

- Markdown: **`react-markdown` + `remark-gfm`**（要求書の「github format」を満たす）
- シンタックスハイライト: **`shiki`**（VS Code と同じ TextMate 文法。
  要求書の「独自実装はしない。OSS で良いのがあれば採用」に合致）
- Markdown エディタ（別要件）も同じレンダラを共有する。

**理由**

renderer 側で npm のライブラリを使う方が自然で、かつ生 HTML を通さない分だけ安全。

**追記（2026-10-15）: GitHub の絵文字と `<details>` / `<summary>`**

- **絵文字**: `remark-gemoji` を加え、`:smile:` などのショートコードを Unicode の絵文字に置き換える。
  トランスクリプトと Markdown ファイルの両方に効く。コード中は置き換えない。
  GitHub 独自の画像絵文字（`:octocat:` など Unicode にないもの）は対象外で、見た目は OS の絵文字フォントに依る。
- **`<details>` / `<summary>`**: **Markdown ファイルの表示（エディタのプレビュー・印刷用表示）に限って**折り畳みとして描く。
  トランスクリプト（エージェントの返答・許可カード）では従来どおり文字として出す。
  - 実装は自前の remark プラグイン（`remarkDetails`）。`rehype-raw` は入れない。
    `<details>`・`<summary>…</summary>`・`</details>` のタグだけを拾って要素にし、それ以外の生 HTML は従来どおり文字として出す。
  - 属性は `open` だけを読む。`summary` の中身はタグを除いた文字列として扱う。
  - 書き方は GitHub と同じ（`<summary>` の後に空行を入れないと、中身は Markdown として解釈されない。
    空行なしで続けた文は文字のまま `details` の中に出す）。入れ子にでき、閉じ忘れは文書の終わりまでを中身とする。
  - 印刷用表示では常に開く（閉じたままだと中身が印刷されない）。
  - ページ内検索（N-1-a）は閉じた `details` の中身も探し、ヒットに移るときにその `details` を開く。

**採らなかった案**:
- **`rehype-raw` + `rehype-sanitize` の許可リスト**: 生 HTML を一度すべて通してから削る方式になり、
  「構造的に安全」が「サニタイズの設定が正しければ安全」に変わる。設定を誤ればエージェントの出力から HTML が混入しうる。
- **トランスクリプトでも描く**: エージェントの出力が折り畳みで内容を隠せることになるため、Markdown ファイルに限った。
  Markdown ファイルもエージェントが書きうるが、作るのは属性なし（`open` を除く）の2要素だけで、
  コードの実行や外部への通信にはつながらない。

## A-3. 対象ユーザーと安全モデル

### A-3-1. 対象ユーザー

**決定**

- 「コードの編集権限がない非エンジニア」は**ユースケースの説明**であり、
  アクセス制御の要求ではない。組織によるポリシー配布の仕組みは設計範囲外。
- 想定する配布形態は **OSS 公開・不特定多数**。
  これは実際に公開するか否かではなく、**使い方を強制しない**という設計原則の宣言。

**設計原則として導かれるもの**

- **前提条件を最小化する。** git が使えることを前提にしない。特定のエージェントを
  必須にしない。特定のワークフローを強制しない。
- **既定値は安全側に、ただし変更可能に。** 押し付けない。
- **エラーは「環境が悪い」ではなく「こうすれば直る」を示す。**
- アプリ外（CLI 等）での操作と共存する。shovel が状態を独占しない。
- UI 言語は英語と日本語の両方を想定する必要がある（F-5 で扱う）。

### A-3-2. 安全モデル：2つの独立した軸

**決定**

責務を2軸に分離する。両者は独立しており、混ぜない。

| 軸 | 決めるもの | 誰が決めるか |
| :--- | :--- | :--- |
| **ワークスペースのアクセス** | Read only / Read-write の2択 | プロジェクト単位の設定（shovel） |
| **Permission の扱い** | 承認をどこまで求めるか | **ACP の Mode**。利用者が選ぶ（shovel は方針を発明しない） |

Permission については shovel 独自のポリシーを作らない。
`session/new` が返す `modes` からセレクタを構成し、`session/set_mode` を送る。
`session/request_permission` が来たら常に承認カードを表示する。
「どこまで自動で許すか」はエージェントの Mode の責任とする。

### A-3-3. Read only の実装強度（要確認事項あり）

クライアント capability の `fs.readTextFile` / `fs.writeTextFile` / `terminal` は
**すべて `false`** とする（完全なサンドボックス内包）。
その結果、**エージェントは shovel を経由せず自分でファイルを書く**。

このため Read only の実装方法は強度が3段階に分かれる。

| 方法 | 強制する主体 | 強度 |
| :--- | :--- | :--- |
| ① マウントを read-only にする | OS / コンテナ | **本物。物理的に書けない** |
| ② エージェントの Mode に任せる | エージェント | 約束にすぎない |
| ③ `request_permission` を shovel が自動拒否する | shovel | **穴がある。採用しない** |

③ が成立しない理由: `session/request_permission` はエージェントが**自主的に**
送るものであり、送らずに書くことを shovel は止められない。ファイル操作を
仲介していないため、そこに強制点が存在しない。

**未決 (N-2 で確定)**: `sbx` が read-only マウントを提供するか。

**検証結果（2026-09-13）**

`sbx create claude .:ro` は拒否される:

```
ERROR: primary workspace must be read/write (remove ':ro' or ':readonly')
```

primary ワークスペースを read-only にはできない。ただし**追加ワークスペースには
`:ro` が使える**（`sbx run --help`: "Additional workspaces can be provided as
extra arguments. Append ':ro' to mount them read-only."）。よって残る道は2つ:

- ~~**抜け道A**: primary にスクラッチ用空ディレクトリを渡して制約を満たし、
  本命のプロジェクトを追加ワークスペースとして `:ro` でマウントする~~
  → **不採用（2026-09-13）。** エージェントから見て不自然な環境
  （cwd が書けない、隣に用途不明の空ディレクトリがある）を作るため、
  エージェントの挙動が乱れたときに原因追跡が困難になる。
  「Hack 的なことはしない」という方針判断。
- **抜け道B**: `--clone`（ホストの git リポジトリを read-only マウント）。
  → 後述 A-3-4 で評価。

**結論**: **OS 強制の read-only は採用しない。** よって shovel は
「読み取り専用」を保証として名乗れない。代わりの安全モデルは A-3-4 で定める。

### A-3-4. 安全モデル：3層（+ 参考: 廃止した④回復）

**決定：「Read only」という設定そのものを廃止する。**

`Project.access`（Read only / Read-write の2択）は設けない。
「一時的な改変は起きるが結果として元に戻す」という定義も**採用しない**。

| 層 | 手段 | 自動/明示 | 守る範囲 |
| :--- | :--- | :--- | :--- |
| **① 隔離** | サンドボックス | 自動 | **プロジェクト外は完全に守られる** |
| **② 予防** | 承認カード（`session/request_permission`） | 自動 | エージェントが**聞いてきたもの**は止められる |
| **③ 方針** | ACP の Mode | 利用者が選ぶ | どこまで聞くかの方針 |

~~④ 回復（git）~~ は **A-3-8 で廃止**した。以下の「Read only を廃止した理由」
自体はこの層の有無と無関係に成立するため、そのまま残す。

**「Read only」を廃止した理由**

検討の経緯は次の通りで、**どの案も「約束」にならなかった**。

1. OS 強制の read-only マウント → `primary workspace must be read/write` で不可。
2. primary をスクラッチにして本命を `:ro` で追加マウント → エージェントから見て
   不自然な環境を作る Hack であり不採用。
3. `--clone` → ホストは守られるがエージェントは自由に書ける。
   ファイラーに成果が現れず、取り出しに `git fetch sandbox-<name>` が要る。
   「ホストを汚さず作業させる」機能であって「閲覧専用にする」機能ではない。
4. `request_permission` の自動拒否 → エージェントが聞かずに書けるため穴がある。
5. セッション終了時の自動 revert → 「Read only とも言えず、必ず回復するとも
   言えない」中途半端な保証になる。

**保証できないものを保証と名乗るのが最も危険**であり、
**中途半端な保証は無保証より悪い**という判断で、概念ごと落とす。

「閲覧だけしたい」という要求は ③（ACP の Mode。Claude Code なら plan モード）
に委ねる。これは A-3-2 の「shovel は Permission の方針を発明しない」と一貫する。

**Read only モードは対応しない。これは最終決定であり、V-1（追加ワークスペースの

### A-3-8. 安全モデル：④ 回復（git ベースの元に戻す）を廃止

**決定（2026-09-17）**: A-3-4〜A-3-7 と N-3-7 で設計した「変更」サイドバー
（`git status`/`git diff` による累積差分の表示と `git restore` による復元）を
**丸ごと廃止する**。ファイル操作の差分検知・復元機能は shovel から無くなる。

**トランスクリプトのツールカードにある「操作単体」の diff（N-3-8 の
`TextDiffView`／クリックで開く Diff ビューア）はこの決定の対象外で、そのまま残す。**
これはエージェントが「今何をしたか」を見るためのものであり、
「戻す」ための累積状態ではないため、以下の理由と無関係に成立する。

**廃止の理由**

- shovel は用途を「既存ソースコードから仕様調査」に限定しない
  （README.md の設計原則「特定のワークフローを強制しない」）。
  想定ユースケースの一つに**壁打ち**（構想・調査結果をエージェントと
  まとめていく使い方）があり、そこでは生成物がソースコードではなく
  ドキュメントやメモそのものである。この用途では「元に戻す」機能は
  作業の腰を折るだけでなく、**誤操作でまとめた内容を消してしまう
  事故要因になる**。
- 「既存ソースコードから仕様調査」という用途では、対象がそもそも
  git 管理下にあることが多く、**復元は使い手が普段使っている git で
  十分に可能**。shovel が専用の復元 UI を持つ必要性が薄い。
- 両者を並べたとき、**復元機能は前者を妨げ、後者には元々不要**という
  非対称が生じる。「用途を限定しない」という設計原則（README.md）に
  照らすと、この機能自体が原則と矛盾していた。

**連動する変更**

- プロジェクト作成時の「git で変更を戻せるようにする」チェックボックスと、
  それに伴う `git init` の自動実行を廃止する（A-3-5 が廃止対象になった理由）。
  git 管理そのものは既存ディレクトリなら引き続き使えるし、エージェント自身が
  必要に応じて `git init`/`git commit` 等を自分の判断で実行することは妨げない
  — **shovel 側が代わりに握らない**、というだけ。
- 安全モデルは①隔離／②予防／③方針の**3層**になる（A-3-4）。
  「読み取り専用は存在しない」という A-3-4 の結論自体は変わらない。
- N-3-7（変更の情報源の二段構え）・N-3-8 の「変更」サイドバー向け入力
  （`UnifiedDiffView`/`diffRowsFromUnified`）を削除する。

## N-3. エディタ / Diff / ファイラー

IDE なら標準で備わっている機能（Diff ビューア、エディタ、ファイルツリー、

### N-3-1. 構成A：Markdown 以外は閲覧のみ

**決定**

| 対象 | 扱い |
| :--- | :--- |
| 画像（png/jpg/gif/webp/avif/bmp/ico/svg、20MB まで） | **アプリ内でプレビュー**（拡張子で判定。main が data URL にして渡す） |
| その他のバイナリ | 「プレビューできません」＋「既定のアプリで開く」ボタン。**押したときだけ** OS の関連付けアプリへ（`shell.openPath()`）。勝手には開かない |
| テキスト（Markdown 以外） | **アプリ内で閲覧のみ**。shiki でハイライトし行番号を付ける。編集不可 |
| Mermaid（.mmd / .mermaid） | 閲覧のみ。**図／コードを切り替えて表示**（既定は図。N-3-2b 追記） |
| Markdown | Markdown エディタ（編集可能） |

**重量級のコードエディタ（Monaco / CodeMirror）は採用しない。**
（→ 2026-10-17 改訂で CodeMirror 6 は採用した。下の「改訂（2026-10-17）: 編集面を CodeMirror 6 にする」。Monaco は引き続き採用しない）

**理由**

- **このアプリは IDE ではなくチャットである。** エージェントとのやり取りが
  Markdown であり、壁打ちのメモも Markdown で足りる。
- 要求書も Markdown だけを「エディタ」と呼び、他は「開く」としか書いていない。
- Monaco はバンドルが数MB、Web Worker 構成が必要、Tailwind / shadcn と
  見た目が合わない。**コードを書くのは AI であって人間ではない**ため過剰。
- 閲覧のみなら、ユーザーの直接編集が ④ の「変更」一覧に混ざる事故も起きにくい。

**将来の拡張余地**: 編集が必要になったら、閲覧ビューを CodeMirror 6 の
`readOnly: false` に差し替えれば UI 構造を変えずに移行できる。

**改訂（2026-10-05）: JSON / YAML は編集できる**

| 対象 | 扱い |
| :--- | :--- |
| JSON（.json）/ YAML（.yaml / .yml） | 編集できる（表示方式は下の「再改訂」で変更） |

- 理由: MCP サーバーの設定など、エージェントに頼むより自分で直したい**設定ファイル**が
  JSON / YAML で書かれていることがある。「コードを書くのは AI」という前提は変えない。
  対象はあくまで設定ファイルで、ソースコード一般を編集可能にはしない（TOML などは
  必要になってから足す）。
- 実装は既存の Markdown エディタ（textarea・autosave・競合コピー・改行コード/BOM の保持・
  UTF-8 以外は表示のみ）を流用する。CodeMirror などは入れない。ハイライトは編集中には付かない。
  英語のスペルチェックの波線は消す。
- 対象拡張子の判定は `src/shared/fileKinds.ts` の `editorLanguageFor` 1か所に置く。
- ファイラーの新規作成は「新規ファイル ▸」のサブメニューにまとめ、
  新規メモ（Markdown）/ 新規メモ（Text）/ 新規図（Mermaid）/ 新規設定（JSON）/ 新規設定（YAML）を並べる。
  JSON は空だと不正なので `{}` を書いて作る。YAML は空で作る。

**再改訂（2026-10-05）: 編集できるテキストの表示方式を2つに統一する**

編集できるテキストファイルはすべて同じエディタ（`TextFileEditor`。旧 `MarkdownEditor`）で開き、
ファイルの種類ごとに2つの方式のどちらかを使う。

| 方式 | 対象 | 切り替え | 既定 |
| :--- | :--- | :--- | :--- |
| 分割・ソース・プレビュー | Markdown / **Mermaid** / **HTML** | 「分割」「ソース」「プレビュー」 | 分割（チャットの横ではソース） |
| 表示・編集 | JSON / YAML / テキスト（.txt） | 「表示」（shiki でハイライト。テキストは色なしで行番号だけ）「編集」 | 表示 |

- **Mermaid も編集できる**ようにした。プレビューは図（`MermaidDiagram`）。打鍵ごとに描き直すと
  重く、書きかけの文法エラーでちらつくので、400ms 待ってから描く。
  これまで `FileViewer` にあった「図／コード」の切り替えと「再読み込み」ボタンは無くした
  （エディタの外部変更検知で自動的に読み直すため。N-3-2b の Mermaid の段落を参照）。
- **JSON / YAML は表示を既定にする。** 設定ファイルは見るだけの場面が多く、編集したい場面の方が
  少ないため。「編集」で textarea に切り替わり、「表示」でハイライト表示に戻る。
- **チャットの横に表示（G-1-9）** は、エディタを共通にした結果そのまま使えるので、
  編集できる4種すべてで使えるようにした（Markdown 以外は強い要望が無く、制限する理由も無い）。
  チャットの横では「分割」を出さない点だけ方式ごとに変わる（表示・編集方式はもともと分割が無い）。
- スペルチェックは Markdown だけ有効（図や設定ファイルのキーに波線が付くため）。
- **テキスト（.txt、2026-10-05 追記）**: 「新規メモ（Text）」で作れる。整形の要らない短いメモ用で、
  UI は JSON / YAML と同じ（表示が既定・行番号・折り返さない）。種類の追加が JSON / YAML と同じ
  経路で済むよう、「表示・編集」方式かどうかは `fileKinds.ts` の `usesViewEditModes` で決める。
- **HTML（.html / .htm、2026-10-15 追記）**: 「新規ページ（HTML）」（アイコン `file-code`）で、
  最小限の雛形（DOCTYPE・`<meta charset>`・`<title>`・空の `<body>`）を書いた `Untitled.html` を作れる。
  プレビューは描いたページそのもの（`HtmlPreview`）で、Mermaid と同じく 400ms 待ってから描き直す。
  AI が書いた HTML をそのまま描くので、閉じ込め方を次のように決めた。
  - `<iframe sandbox="allow-popups" srcdoc>` に流し込む。スクリプト・フォーム・親ウィンドウの遷移は
    動かず、アプリ本体とは別の（不透明な）origin になる。
  - `srcdoc` の iframe は親ページの CSP を引き継ぐので、外部の画像・CSS・フォントは読み込まれない
    （外への通信が起きない）。インラインの `<style>` / `style` 属性と `data:` の画像は効く。
  - リンクは、先頭（DOCTYPE の直後）に `<base target="_blank">` を差し込んで新しいウィンドウとして
    開かせ、既存の `setWindowOpenHandler` が http(s) / mailto だけを外部ブラウザへ渡す
    （`allow-popups` はこのため）。iframe の中で遷移させると、親の CSP（`frame-src` は
    `default-src 'self'` に落ちる）で塞がれてエラー画面になるだけで、`will-frame-navigate` も発火しない
    ことを確かめた。ページ内リンク（`#id`）もこの扱いになるため、プレビュー内ではスクロールしない。
  - 相対パスの画像・CSS（`./img.png` など）は解決できない（`srcdoc` の基準 URL は `about:srcdoc`）。
    プロジェクトのファイルを配信する仕組みを足すことになるので見送る。
  - 背景は白に固定する（ブラウザで開いたときと同じ見え方にするため、テーマには合わせない）。
  - 印刷用表示（N-3-10）にも対応する（N-3-10 の「HTML の印刷」）。

**編集の補助（2026-10-05 追記）**: エディタは素の textarea のまま（CodeMirror などは入れない）で、
設定ファイルを直すのに要る分だけ足す（`src/renderer/main-window/textEditing.ts`）。

- **Tab / Shift+Tab**: フォーカスを移さず、スペース2つのインデントを増やす・減らす。複数行を
  選んでいれば各行に効く。`execCommand('insertText')` で入れるので元に戻す（Cmd/Ctrl+Z）が効く。
  全種類で有効（Markdown のリストの入れ子にも使える）。
- **行番号**: Markdown 以外（Mermaid / JSON / YAML / テキスト）。行番号と折り返しは両立しない（折り返すと1行が
  複数行に見えて番号がずれる）ため、これらは折り返さず横スクロールにする。Markdown は文章で
  折り返しの方が大事なので、行番号を付けない。
- **JSON の書式チェック**: `JSON.parse` の結果をステータスバーに「JSON の書式に誤りがあります
  （N 行目 M 列目）」と出し、押すと編集に切り替えてその位置にカーソルを置く（表示モードでも出す）。
  YAML のチェックはライブラリの追加が要るので見送る。
- 編集中のハイライトは付けない（付けるなら CodeMirror の導入で、この決定の見直しになる）。

（→ 2026-10-17 改訂で、ここの補助は CodeMirror 6 の機能に置き換える。下の「改訂（2026-10-17）」）

**改訂（2026-10-17）: 編集面を CodeMirror 6 にする**

**決定**: `TextFileEditor` の編集面（textarea）を **CodeMirror 6** に替える。Monaco は引き続き採用しない。

- **編集できる対象は変えない。** エージェントへの指示などに使う設定ファイル・メモ・出力物
  （Markdown / Mermaid / HTML / JSON / YAML / テキスト）だけで、ソースコード一般は編集可能にしない。
  「コードを書くのは AI であって人間ではない」という前提は維持する。

**理由**

- 対象が設定ファイル・メモ・出力物でも、編集中のハイライト・インデント・行番号は要る。textarea に自前で
  足してきた補助（Tab インデント、行番号の列とスクロールの同期、JSON の誤り位置への移動、折り返しを考えた
  選択位置へのスクロール）が増えてきており、これ以上自前で足すより CodeMirror に任せる方が小さく済む。
- 当初の理由のうち「直接編集が ④ の『変更』一覧に混ざる」は、A-3-8 で変更サイドバーを廃止して既に無い。
- CodeMirror 6 は Web Worker が要らず、ネイティブモジュールも無い（F-2b に抵触しない）。見た目は自前の
  テーマで Tailwind / shadcn に合わせられる。Monaco を採らない理由（数MB・Worker 構成・見た目）はそのまま残る。

**方針**

- 拡張は必要なものだけを入れる（全部入りの `basicSetup` は使わない）: 行番号・元に戻す（履歴）・
  インデント（`indentWithTab`）・検索・色付け（下の「色付けは shiki」）。CodeMirror の言語パッケージは入れない。
- **矩形選択と行末の空白（2026-10-17 追記）**:
  - 矩形選択（Alt / Option+ドラッグ。押している間はカーソルが十字になる）を入れる。そのために複数の選択範囲を
    許し（`allowMultipleSelections`）、選択とカーソルを CodeMirror が描く（`drawSelection`）。複数選択を
    許したので、検索の Mod-d（同じ語を次々に選択へ足す）も効くようになった。
  - 行末の空白を塗って見せる（`highlightTrailingWhitespace`）。エディタは設定ファイル用で、YAML などでは
    行末の空白が気づきにくい誤りになるため。Markdown（行末の空白2つは改行の意味）も区別せず塗る。
  - 見送ったもの: 不可視文字の表示・カーソル行の強調・選んだ語と同じ語の強調・括弧の対応の強調・
    括弧の自動補完（日本語の文章で勝手に括弧が入るのは邪魔）・自動補完・すべての空白の表示・
    JSON の誤りのエディタ内表示（`@codemirror/lint`）。折りたたみ・入力に合わせた自動インデント・
    コメントの切り替え（Mod-/）は言語パッケージが要るので使えない。
- React のラッパー（`@uiw/react-codemirror`）は使わず、`@codemirror/state` / `@codemirror/view` の
  `EditorView` を直接作って持つ（`src/renderer/main-window/codeEditor.ts`）。中身の正本は CodeMirror で、
  React の state から CodeMirror へ中身を渡し直すことはしない（プレビュー・ステータスバー用に、
  CodeMirror から state へは写す）。外部変更の読み直しは、変わった範囲だけを書き換えるトランザクションで入れ、
  元に戻すの履歴には積まない。
  - 理由: 外部変更の読み直し・競合コピー・書き出し・一致箇所や誤り位置への移動は、どれもエディタを命令的に
    操作する処理である。ラッパーの `value` で中身を差し替えると、元に戻すの履歴とカーソル位置が乱れやすい。
- エディタは読み込みが済んだら作り、プレビューだけ・「表示」の間も隠して残す（切り替えても元に戻すの履歴が消えない）。
- 自動保存・競合コピー・改行コード/BOM の保持・UTF-8 以外は表示のみ（N-3-2）は変えない。
  CodeMirror は中身の改行を LF にそろえるので、保存時は元の改行コードへ戻す経路を通す。
- ライト/ダークのテーマとファイル表示の文字の大きさ（`editorFontSize`、G-1-13）に合わせる。
- **色付けは shiki（2026-10-17 追記）**: 当初は CodeMirror の言語パッケージで色を付け、shiki に近い色を
  当てていたが、「表示」と「編集」を切り替えると色が変わるのが気になったため、エディタの色も shiki で付ける
  （`src/renderer/main-window/shikiHighlight.ts`。shiki の `codeToTokens` の結果を CodeMirror の装飾にする。
  依存は足さない）。閲覧・「表示」・トランスクリプトと文法も配色（github-light / github-dark）も同じになり、
  Mermaid にも色が付く。
  - shiki は非同期なので、開いた直後と打鍵の後（150ms 待ってから全体を解析し直す）は少し遅れて色が付く。
    それまでは直前の色を編集に合わせてずらして使う（ちらつかない）。
  - 20万文字を超える中身には色を付けない（打鍵ごとに全体を解析し直すため）。
  - 余白と行番号の位置は「表示」と揃え、切り替えても文字が動かないようにする。ダークの「表示」に付いていた
    shiki の地の色（`--shiki-dark-bg`）は、行番号付きの表示（`.shiki-lines`）では外し、エディタと同じアプリの
    地の色にする。
- スペルチェックは従来どおり Markdown だけ。
- **行番号はすべての種類に付ける（2026-10-17 追記）。** Markdown は折り返し、他は折り返さない。
  textarea では行番号と折り返しが両立しなかったので Markdown には付けていなかったが、CodeMirror では
  両立する（折り返した続きには番号が付かない）。行番号の無い Markdown に違和感があったため付けた。
- 上の「編集の補助」は次のように置き換える。
  - Tab / Shift+Tab: `indentWithTab`。Esc の後の Tab でフォーカスを外へ移せる。
  - 行番号: CodeMirror の行番号（Markdown にも付ける）。
  - JSON の書式チェック: ステータスバーの表示と、押して誤りの位置へ移る動作は残す。移るのは CodeMirror の選択で行う。
    YAML のチェックは引き続き見送る。
  - 中身検索の一致箇所へ移る（N-3-11）のも CodeMirror の選択とスクロールで行う。

**検索（Cmd/Ctrl+F）の分担**

ページ内検索（N-1-a）は CodeMirror の中身を探さない。どちらが受け持つかを次のように決める。

| 場所 | 表示 | Cmd/Ctrl+F |
| :--- | :--- | :--- |
| ファイルのタブ | ソース・分割・「編集」 | CodeMirror の検索パネル |
| ファイルのタブ | プレビュー・「表示」 | ページ内検索 |
| チャットの横のエディタ（G-1-9） | — | フォーカスが CodeMirror にあれば CodeMirror の検索パネル、無ければページ内検索（CodeMirror の中身は対象外） |

- ファイルのタブはフォーカスではなく**表示方式で決める**。どちらが出るかを利用者が予想しやすいため。
- 分割ではプレビュー側は探せない（同じ中身をソース側で探す）。ソース側で移った位置にプレビューは追従しない。
- チャットの横のエディタだけフォーカスで決めるのは、表示方式で決めるとソース表示の間はトランスクリプトを
  探せなくなるため。
- 検索パネルは CodeMirror のものをそのまま使い、見た目はテーマでページ内検索に寄せる。文言は i18n で訳す。
- 取り次ぎは `src/renderer/main-window/editorSearch.ts`。ソースが見えているタブのエディタが自分の検索を登録し、
  ページ内検索は Cmd/Ctrl+F を受けたとき、見えている登録先があればそちらの検索パネルを開く。フォーカスが
  エディタにあるときは、エディタが自分でキーを処理する（ページ内検索は何もしない）。
- ページ内検索を開いたまま表示方式を切り替えたら（プレビュー → ソースなど）ページ内検索は閉じる。

**採らなかった案**

- **ページ内検索で CodeMirror の中身も探す**: CodeMirror は画面外の行を描かないので見えている範囲しか
  ヒットせず、CodeMirror が DOM を描き直すと CSS Custom Highlight の Range が壊れる。
- **ページ内検索の見た目のまま、裏で CodeMirror の検索を操作する**: UI は1つになるが、ページ内検索に
  CodeMirror 向けの経路を足すことになる。CodeMirror の検索パネルをそのまま使う方を採った。
- **どこでもフォーカスで決める**: ファイルのタブでは、どちらが出るかがフォーカスの位置次第になって分かりにくい。
- **CodeMirror の言語パッケージで色を付け、配色だけ shiki に寄せる**: 文法の解釈が違うので、色の付く単位が
  揃わない（実装して見比べ、気になった）。

**右クリックメニュー**: G-1-16。

### N-3-2. バイナリ判定

**決定**: 拡張子では判定しない。**先頭数 KB に NULL バイトがあるか**で判定する。
バイナリなら、確認（ボタン）のうえ `shell.openPath()` で OS の関連付けアプリへ渡す。
例外として、プレビューする画像（N-3-1 の表）だけは拡張子で先に振り分ける
（SVG はテキストなので NULL バイト判定ではバイナリにならないため）。
UTF-16 は NULL バイトを含むのが普通なので、BOM があれば NULL バイト判定より先に
テキストとして扱う。

**文字コード・改行コード（2026-09-30 追記）**: テキストの閲覧・Markdown エディタの下端に
ステータスバー（ファイルサイズ・文字コード・改行コード）を出す。文字コードは
UTF-8 / UTF-8 BOM / UTF-16 LE・BE（BOM）/ Shift_JIS を判定する（`src/main/domain/textEncoding.ts`）。
読み込み時に改行を LF へ揃え、書き戻し時にディスク上の元の改行コードと BOM へ戻す
（エディタが CRLF を LF にしてしまい、1文字の編集で全行の改行が書き換わるのを防ぐ）。
UTF-8 以外のファイルは UTF-8 で書き戻すと壊れるため、Markdown エディタでは表示のみにし、
main 側の書き込みも拒否する。

**画像のステータスバー（2026-10-02 追記）**: 画像のプレビューの下端にも、ファイルサイズと
幅×高さ（px）を出す。幅×高さは画面側で `img.naturalWidth/Height` から取る（ライブラリは
足さない）。SVG はルートに `width`/`height` が絶対値で両方あるときだけ数値を出し、
それ以外（viewBox だけ・% 指定・指定なし）は「—」にする。Chromium はそうした SVG にも
既定の 300×150 を返すため、そのまま出すと誤った値になる。

### N-3-2b. コードブロックのハイライトと Mermaid（2026-10-01）

**決定**:
- Markdown（トランスクリプト・エディタのプレビュー共通）の言語付きコードブロックは
  shiki でハイライトする。確定したブロックだけが Markdown として描かれるので、
  ストリーミング中にハイライトし直すことはない。
- ```` ```mermaid ```` はコードのまま見せ、コードブロック右上の専用ボタンから開く
  **ポップアップでだけ図を描く**（`MermaidDialog`）。トランスクリプトの中に直接は描かない。
  ボタンは補助的なコピーとは区別し、コードブロックの左上に常時表示する目立つボタン
  （Mermaid の公式ロゴ ＋「図を表示」、ブランド色 `#FF3670`。ロゴは simple-icons の
  CC0 版を `icons/MermaidIcon.tsx` に同梱）にする。

- 例外: Markdown の**印刷用表示**（別ウィンドウ）では図をその場に埋め込む（N-3-10）。
  下の「ポップアップにした理由」は、内容を開いた時点で固定する印刷用表示には当てはまらない。

- トランスクリプト（履歴タブを含む）では、6行以上のコードブロックを最初の5行に畳み、
  「すべて表示（N行）」で開く（Mermaid のブロックも同じ）。Markdown エディタの
  プレビューでは畳まない（自分で書いている文書は常に全体を見せる）。コピーは常に全文。

**理由（ポップアップにした理由）**: 直接描くと、ストリーミング中の書きかけの図
（文法エラー）、非表示のタブで描いたときの寸法崩れ、テーマ切り替え時の描き直し、
エラー表示の置き場所をすべて扱う必要がある。ポップアップなら「開いた時点の確定した
コードを、その時点のテーマで描き、失敗したらその場でエラーと元のコードを出す」
だけで済む。

**サイズ**: `mermaid` は大きい（ビルド後のレンダラ出力が約 12MB → 約 23MB）。
起動時には読み込まず、プロジェクトのウィンドウが開いた後の空き時間に読み込んでおく
（`preloadMermaid`）。インストーラのサイズ増は受け入れる。ネイティブモジュールは含まない。

**安全性**: ポップアップでも SVG を DOM に差し込むことに変わりはないため、
`securityLevel: 'strict'`（図の中の HTML・クリック時のスクリプトを無効）で描く。
CSP の変更は不要（`unsafe-eval` を要しない）。

**Mermaid のファイル（2026-10-02 追記。2026-10-05 に N-3-1 の再改訂で編集可能に変更し、
下記の「図／コード」切り替え・「再読み込み」・閲覧のみは廃止）**: `.mmd` / `.mermaid` を Filer から開くと、
タブ全体を使って図を描く（`FileViewer`。ポップアップではない）。上端の「図／コード」で
切り替え（既定は図、コードは shiki の `mermaid` でハイライト）、「再読み込み」で
ディスクから読み直す。他のテキストと同じく閲覧のみで、編集・自動の再読み込みはしない
（外部変更の検知は V-8 が未決のため、エージェントが書き換えたら手で読み直す）。
ポップアップにした理由のうち、書きかけの図はファイルでは起きない。非表示のタブでも
`mermaid.render` は body 直下の一時要素で寸法を測るので崩れない。テーマの切り替えは
`<html>` の `dark` クラスを見て描き直す（`MermaidDiagram`、ポップアップと共通）。
文法エラーはタブの中にエラーと元のコードを出す。
Filer の右クリックから「新規図（Mermaid）」で `Untitled.mmd` を作れる。空のファイルは
文法エラーになるため、小さな見本（`flowchart TD` の2ノード）を書いた状態で作る。
メニューの名前は「新規Markdownファイル」「新規Mermaidファイル」だと先頭が似ていて
取り違えやすいので、用途を先に出して「新規メモ（Markdown）」「新規図（Mermaid）」とし、
図のほうは Mermaid のロゴ（ブランド色）で見分けられるようにした。

**大きい図の表示（2026-10-19 追記）**: Mermaid ファイルのプレビューとポップアップ（`MermaidDialog`）では、
図を拡大・縮小・移動できるようにした（`MermaidViewer`、拡大率の計算は `diagramZoom.ts`）。
それまでは幅に収まるよう縮めるだけだったため、横に長い図（左から右のフローチャート、登場人物の多い
シーケンス図など）は文字が潰れて読めず、拡大する手段もなかった。

- **初期状態は「幅に合わせる」**（従来どおり。本来の寸法より大きくはしない）。
- 図の右上に重ねたツールバー: 縮小 / 拡大率（押すと等倍 100%）/ 拡大 / 幅に合わせる / 全体を表示
  （幅と高さの両方に収める。これも本来の寸法より大きくはしない）。拡大・縮小は決まった段階
  （2%〜800%）を順に移る。
- Cmd/Ctrl＋ホイール（トラックパッドのピンチを含む）で、ポインタの位置を中心に拡大・縮小する。
- 図が表示領域からはみ出しているときは、ドラッグで移動できる（掴むカーソルになる）。図の中の文字は
  ドラッグで選択できなくなるが、コピーしたいときはソースから取れる。
- ダブルクリックで「合わせる ⇔ 等倍」を切り替える（等倍にするときはポインタの位置を中心にする）。
- 合わせるモードは、表示領域の大きさが変わるたび（分割の切り替え・ウィンドウの大きさ・最大化）に合わせ直す。
- **描き直しても拡大率とスクロール位置を保つ**（エディタは編集の 400ms 後に描き直すので、そのたびに
  「幅に合わせる」へ戻ると使えない）。拡大率は保存せず、プレビューを閉じる（ソースだけに切り替える・
  タブを閉じる）と初期状態に戻る。
- ポップアップには見出しの右（閉じるボタンの左）に**最大化**ボタンを置き、ウィンドウいっぱいに広げられる。
  「全体を表示」が表示領域の高さを基準にするので、ポップアップの高さは中身に依らず固定（85vh）にした。
- **印刷用表示には入れない**（用紙の幅に収めるのが正しく、操作の UI は印刷の邪魔になる）。従来の `MermaidDiagram` のまま。

**実装上の注意**: 拡大は CSS の `transform: scale` ではなく、SVG の `width`/`height` を「`viewBox` の寸法 × 倍率」に
する。ベクターのまま描かれ、普通のスクロールバーがそのまま使える。表示領域の幅は `scrollbar-gutter: stable` で
固定する（縦のスクロールバーが出入りするたびに幅が変わり、「幅に合わせる」が揺れるのを防ぐ）。
ライブラリ（svg-pan-zoom など）は足していない。

### N-3-3. Markdown エディタ

**決定**: **分割ビュー（左=Markdown ソース / 右=プレビュー）を基本とし、
どちらか一方の単独表示にも切り替えられる**ものとする。

WYSIWYG 風（Typora / Obsidian のようなインラインプレビュー）は採用しない。
ProseMirror ベースの実装が必要になり、実装量が跳ね上がるため。

プレビューのレンダラは D-5 で決めた `react-markdown` + `remark-gfm` + `shiki` を
トランスクリプトと共有する。

**表示モードのアイコン（2026-09-30 追記）**: 「分割」`columns-2`、「ソース」
`square-code`、「プレビュー」`eye`。チャットタブの右に添えたとき（G-1-9）は
横幅が狭いため「分割」を出さず、ソースとプレビューの切り替えだけにする
（既定はソース）。Markdown タブ単独のときは3モードのまま。

**閉じたときの書き出し（2026-09-30 追記）**: autosave は約600msのデバウンスを
挟むため、タブを閉じる・チャットの横から外すときにもその時点の編集を書き出す
（書き出さないと、閉じる直前の編集が失われる）。

### N-3-10. Markdown / HTML の印刷用表示（2026-10-07、HTML は 2026-10-15 追記）

**決定**: Markdown エディタ（`.md` のタブ、チャットの横に添えたときも）に「印刷用表示」ボタンを置く。
押すと**別ウィンドウ**（`print-preview.html`、ファイルごとに1枚）で文書全体を描き、そこの「印刷…」で
OS の印刷ダイアログを出す（`webContents.print`）。PDF にするのも OS に任せる（macOS の「PDF として保存」、
Windows の「Microsoft Print to PDF」）。

- ```` ```mermaid ```` は**コードではなく図として埋め込む**（N-3-2b の例外）。通常のプレビューは従来どおりコードのまま。
- 描く内容は**開いた時点のディスクの内容**。開く前にエディタの自動保存待ちを書き出す。
  自動では追随せず、「読み込み直す」か、エディタのボタンをもう一度押すと描き直す（同じファイルのウィンドウを再利用）。
- **図とハイライトがすべて描き終わるまで「印刷…」を押せない**（`RenderTracker`。図が空白のまま印刷されるのを防ぐ）。
  文法エラーの図は、その位置にエラーと元のコードを出して印刷できる。
- テーマは**常にライト**、文字サイズは設定に依らず固定（10.5pt）。コピーや「図を表示」のボタンは出さない。
- 印刷用の CSS: コードブロックは横スクロールさせず折り返す。図・コードブロック・表・引用は
  ページの途中で分けない（1ページに収まらないものは分かれる）。見出しの直後で改ページしない。余白は `@page` で 15mm。
- 背景も印刷する（`printBackground: true`）。コードブロックの地の色を画面と揃えるため。
- プロジェクトのウィンドウを閉じると、そのプロジェクトの印刷用表示も閉じる。

**採らなかった案**:
- **今のタブのまま `@media print` で印刷する**: タブ・サイドバーなどを印刷時に消して回る必要があり、
  UI を変えるたびに印刷が壊れうる。テーマや文字サイズの設定から切り離すのも難しい。
  また、図を印刷の直前に描くことになり、描き終わりを待つ制御が別に要る。
- **アプリ内でページ単位のプレビュー**: Chromium の実際の改ページは shovel からは見えない。
  ページ単位の確認は OS の印刷ダイアログのプレビューに任せ、画面の名前も「印刷用表示」にした。
- **`printToPDF` で直接 PDF を書き出す**: 用紙・余白・プリンタの選択を自前で持つことになる。必要になれば後から足せる。

**HTML の印刷（2026-10-15 追記）**: HTML のエディタにも同じ「印刷用表示」ボタンを置く。

- 印刷用表示のウィンドウには、エディタのプレビューと同じ `HtmlPreview`（sandbox の iframe）で
  ページを A4 幅に見立てて描く。これは**画面用の表示**で、ページの `@media print` は効いていない旨を
  上端に出す（「印刷の仕上がりは印刷ダイアログで確認できます」）。
- 「印刷…」では、表示している内容を main に渡し、**そのページだけを読み込んだ非表示のウィンドウ**で
  `webContents.print` する（`src/main/windows/htmlPrint.ts`、印刷が終わったら閉じる）。
  ページ自身の `@page` / `@media print` / 改ページの指定がそのまま効く。
  - JavaScript は無効（`webPreferences.javascript: false`）。
  - ページは専用の保存しないセッション（`shovel-html-print`）の `shovel-print://<uuid>/` から配信し、
    CSP（`default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:`）で外部の
    画像・CSS・フォントを読ませない（プレビューと同じく、外への通信を起こさない）。
  - 遷移・新規ウィンドウ・権限の要求はすべて拒否する。
- Markdown と違ってテーマ・文字サイズの固定や `print.css` は当てない（ページの見た目はページ自身が決める）。
  背景は印刷する（`printBackground: true`）。
- **採らなかった案**: 印刷用表示の iframe の高さを中身に合わせて、ウィンドウごと印刷する。改ページ自体は
  されることを確かめたが、ページ自身の `@page` が効かず、画面幅と用紙幅で高さが変わると末尾が欠けうる。
  中身の高さを測るために iframe に `allow-same-origin` を付ける必要もある。

**対象範囲**: Markdown（`.md`）と HTML（`.html` / `.htm`）。トランスクリプトの印刷は、ユーザー/エージェントの区別やツール呼び出しの
扱いなど別の論点が多いので扱わない。

**実装上の注意**:
- `mermaid.render` は同時に複数の図を描くと終わらないことがあるので、`renderMermaid` は呼び出しを1つずつ順に処理する。
- `Markdown` の `components` は `useMemo` で固定する。描画のたびに作り直すとコードブロックが毎回作り直され、
  描画完了の通知で親が描き直される印刷用表示では、図の描画が終わらなくなる。

### N-3-11. ファイラーの中身検索（2026-10-08）

**決定**: ファイル名ではなく**ファイルの中身**を探す検索を、ファイラーに付ける。見た目と操作は
ローカルセッション検索（C-6、`LocalSearchDialog`）に揃える。

- **入口は2つ**:
  - ファイラーの見出しの右、更新ボタンの隣に 🔎。範囲はプロジェクト全体（前回の範囲が残っていればそれ）。
  - フォルダの右クリック「このフォルダ内を検索」。検索語はそのままで、範囲だけそのフォルダに替える。
    ダイアログに「範囲: docs/」と ✕ を出し、✕ でプロジェクト全体に戻す。
  - タブバー・ツールバー・ショートカットには置かない。C-6 と同じく、置き場所だけで「何を検索するか」が
    伝わるようにする（ページ内検索 Cmd/Ctrl+F・セッション検索と取り違えない）。
- **ダイアログは閉じても検索語・範囲・結果を覚えておく**（プロジェクトごと、ウィンドウを閉じるまで。
  ファイラーを閉じても残る）。次に 🔎 を押すと前回の結果がすぐ出て、裏で検索し直して差し替える。
  最後に開いた結果には印を付ける。当たったファイルを1つずつ開いて見ていく使い方のため
  （セッション検索は「1件探して開く」使い方なので覚えない）。
- **結果の単位はセッション検索と同じ**: 1ファイル1行。ファイル名（太字）＋最初の一致を含む行
  （一致だけ太字）＋右寄せのフォルダと行番号。最大100件で打ち切り、その旨を出す。
- **行を押すと、そのファイルを開いて一致箇所へ移る**（`openFile` の `at` → `FileReveal`）。
  - ハイライト表示（ビューア、JSON / YAML / テキストの「表示」）: その行を画面の中央へ寄せ、一致箇所を
    CSS Custom Highlight API（`shovel-reveal`）で塗る。
  - ソースが見えているエディタ（分割・ソース・編集）: エディタで一致箇所を選択し、その行を画面の中央へ寄せる。
  - Markdown / Mermaid が「プレビュー」だけのとき: ソースが見えるモードへ切り替えてから選択する。
- **検索対象**:
  - `.` で始まるフォルダと `node_modules` は、どの深さでも中に入らない。範囲として直接選んだフォルダは探す。
    検索しないものは、ダイアログの見出し横の ⓘ のツールチップに箇条書きで書く（普段は要らない情報なので
    常に出しておかない。対象が増えても行を足すだけで済む）。
    ツールチップの描き方は G-1-15。
  - バイナリ・UTF-8 以外（Shift_JIS 等）・2MB を超えるファイル・シンボリックリンクは読まない。
  - 大文字小文字は区別しない部分一致。正規表現・単語単位などのオプションは付けない。
- **実行はホスト側の Node `fs`**（`src/main/domain/fileSearch.ts`）。`sbx exec` は通さず、`grep` / `rg` にも
  頼らない（ホストに入っている前提を置かない）。浅い階層のファイルから順に探す。呼び出し元ごとに世代番号を
  持ち、新しい検索に追い越されたら途中でやめる（`localSearch.ts` と同じ）。

**採らなかった案**:
- **「無視対象も含める」チェックボックス（`.gitignore` に従う）**: 「無視対象」が何を指すのか、
  非エンジニアには伝わらない。除外したいのは実質 `node_modules` と `.git` などの `.` 始まりのフォルダ
  なので、固定の規則にして画面に書いておく方が分かりやすい。
- **ファイラーの中で、ツリーと結果一覧を入れ替える（VS Code の検索パネル風）**: 結果が残る利点はあるが、
  セッション検索と見た目がずれ、作り直しも大きい。「閉じても覚えておくダイアログ」でほぼ同じ使い方ができる。
- **1ファイルの全一致を並べる**: 非エンジニアには情報が多い。同じファイル内の次の一致は、開いた後に
  Cmd/Ctrl+F（ページ内検索）で辿れる。

### N-3-4. ファイルツリー

**決定**: **`react-arborist`** を採用する。仮想スクロールと D&D が最初から
含まれており、要求書の「移動（ドラッグ&ドロップも可）」を素直に満たす。

- **遅延展開**（展開したフォルダだけ `readdir`）。
- ファイル操作（リネーム・削除・移動・コピー・新規ディレクトリ/新規ファイル作成）
  は**ホスト側の Node `fs`** で実行。バインドマウントなので同じファイルであり、
  `sbx exec` より速い。
  - git だけサンドボックス内で実行するのは、**`fs` はホストに必ずあるが
    git は無いかもしれない**ため（A-3-7）。
- **新規作成（ディレクトリ / Markdown / Mermaid ファイル）**: 右クリックしたノード
  （ディレクトリならその直下、ファイルならその親）、または空白部分の右クリック
  でプロジェクトルート直下に作成できる。既定名（`New Folder` / `Untitled.md` / `Untitled.mmd`）
  が衝突する場合は `findAvailableName`（`filerService.ts`）で「name 2」方式の
  連番を自動で振る。作成後は既存のインラインリネーム UI にそのまま入り、
  ユーザーが名前を確定する。
- **コピーはクリップボード方式**（VSCode の Alt/Cmd + ドラッグ方式ではなく、
  右クリック「コピー」→ 別ノードで右クリック「貼り付け」）。貼り付け先の
  衝突回避にも同じ `findAvailableName` を使うため、同一フォルダへの貼り付け
  （＝複製）もエラーにならず「name 2」として成立する。
- **アプリ外（Finder / エクスプローラー等）からの取り込み（2026-09-30 決定）**:
  OS のファイラーでコピーしたファイル・フォルダの「貼り付け」と、ツリーへの
  ドラッグ＆ドロップに対応する。**どちらもコピーであり移動ではない**
  （VS Code と同じ。JetBrains は移動だが、元の場所のファイルを消さない方が
  「取り返しをつける」原則に合う）。同名は `findAvailableName` の「name 2」採番。
  **進捗表示は出さない**: エージェントに読ませる資料をプロジェクトへ入れる用途を
  想定し、巨大・大量のコピーは想定しない。
  - OS のクリップボードのファイル一覧は、Electron 44 で作り直された
    `clipboard.read()` の `text/uri-list` で読む。これは各 OS のファイル参照形式
    （Windows: `CF_HDROP`、macOS: `NSFilenamesPboardType`、Linux: `text/uri-list`）に
    対応付けられており、OS ごとの読み分けは要らない（Electron 43 までは OS ごとの
    形式を直接読んでいて、Windows は先頭の1件しか取れなかった）。Linux では
    `text/uri-list` を出さないファイルマネージャー向けに `x-special/gnome-copied-files`
    も見る。ネイティブモジュールは使わない（F-2b）。
  - アプリ内の「コピー」と OS のクリップボードの両方があるときは、アプリ内で
    コピーした後に OS 側の中身が変わっていれば、OS 側（アプリ外のファイル）を
    貼り付ける。
  - ドロップされたファイルのパスは `webUtils.getPathForFile` で得る（Electron 32
    以降 `File.path` は無い）。
- **更新ボタン（2026-09-30 決定）**: ファイラー見出しの右（旧「.git」トグルの
  位置）に更新ボタン（`refresh-cw`）を置き、展開したことのあるフォルダを浅い順
  に読み直す。N-3-6 の「ターン終了時の読み直し」だけでは、Finder やターミナル
  での変更が次のターンまで反映されないため。
- **フォルダを OS のファイラーで開く（2026-09-30 決定）**: フォルダ（と空白部分＝
  プロジェクトのルート）の右クリックに「Finder で開く」／「エクスプローラーで
  開く」（Linux は「ファイルマネージャーで開く」）を置く。ツリー上のクリックは
  「展開」なので、文言に OS のファイラー名を入れて区別する。
- **ファイルはダブルクリックか Enter で開く（2026-10-02 決定）**: シングルクリック
  （と矢印キーでの移動）は選択だけにする。続けて見ていくだけでタブが増え、閉じるのが
  大変になるため。フォルダはシングルクリックで開閉のまま。Enter はフォーカス中の
  ファイルを開き、フォルダなら開閉する（react-arborist の既定の「Enter で名前変更」は
  横取りする。名前変更は右クリックから）。VS Code のような「シングルクリックで仮の
  タブ、ダブルクリックで固定」は、タブの状態が増える割に得るものが少ないので採らない。
- **ファイルを右クリックから「既定のアプリで開く」は採用しない（2026-10-02 決定）**:
  `shell.openPath()` は `.sh` / `.command` / `.app` / `.exe` / `.bat` などをホストで
  そのまま実行し得る。エージェントが書いたファイルをホストで実行すると、①の隔離を
  ファイラーの1クリックで越えてしまう。拡張子での拒否・確認ダイアログなどで防ぐと
  仕様も実装も複雑になる割に、取りこぼしの不安が残るため、機能ごと入れない。
  バイナリのビューアの「既定のアプリで開く」ボタン（N-3-1）は従来どおり。

### N-3-5. ツリーの既定表示

**決定**

| 対象 | 既定の表示 |
| :--- | :--- |
| 通常のファイル | 通常表示 |
| 隠しファイル（`.env` 等） | **通常表示**（要求書の「隠しファイルも AI に参照される」と整合） |
| `.gitignore` 対象（`node_modules`, `dist` 等） | **薄く（グレーで）表示。** 隠さず視覚的に後退させる |
| `.git` ディレクトリ | **常に非表示**（2026-09-30 改定。表示トグルは廃止） |

**`.git` の表示トグルを廃止した理由（2026-09-30）**: 「.git」とだけ書かれた
チェックボックスは非エンジニアに意味が伝わらず、差分の追跡など別機能の名残に
見えてしまう。`.git` の中身を shovel の中で見る用途は想定しないため、トグルごと
なくし、その位置は更新ボタン（N-3-4）に使う。

`.gitignore` の判定は **`ignore` npm パッケージ**（ホスト側）で行う。
`git` コマンドを呼ばないため、非 git プロジェクトでもホストに git が
無くても動く。

`node_modules` は `.gitignore` 対象として薄くなり、遅延展開により
開かなければ `readdir` も走らないため、性能問題は起きない。

### N-3-9. 巨大ディレクトリ・開けないディレクトリ（open-issues.md D-4、2026-09-30 決定）

**決定**: ノードの展開で `readdir` が失敗したとき（権限エラー、Windows の
`MAX_PATH`、その他 OS 由来のエラーなど）は、**原因を区別せず一律に**、
そのノードの下へ淡色の「…」プレースホルダを1行表示するだけに留める。エラー
ダイアログやトースト通知は出さない。ホバー時のツールチップで「このフォルダの
中身は表示できません」程度を伝える。

**理由**: `.gitignore` 対象（`node_modules` 等）は N-3-5 で既に薄く表示され、
遅延展開（N-3-4）により開かない限り性能問題も起きない。それでも展開しようと
して失敗するのは、通常はユーザーが深く調べたいとは思わないディレクトリ
（壊れたシンボリックリンク、権限の無いフォルダ、Windows で極端に深い
`node_modules` など）であるため、通知で気を引く必要は無く、「下位階層は
あるが表示できない」と分かる程度の軽い表示で十分と判断した。

### N-3-8. Diff ビューア：自前の行差分、Side by Side（既定）と unified（2026-10-07 改訂）

**決定**: 差分計算も描画も**自前で書く**（`src/shared/diff.ts` ＋
`shared/components/DiffView.tsx`）。差分ライブラリは足さない。

- **表示は Side by Side（左右2列、既定）と unified（1列）の2種類。**
  - 既定値は設定の「差分の表示」（`diffLayout`、既定 `split`）。Diff ビューの
    見出しのトグル（左右 / 1列）では、**そのモーダルを開いている間だけ**切り替わる
    （設定は書き換えない）。
  - Side by Side のときだけモーダルを広げる（`max-w-7xl`、unified は従来の `max-w-3xl`）。
  - **Side by Side は長い行を常に折り返す**（GitHub と同じ）。左右は1つのグリッド行
    なので高さが揃い、横スクロールは無い（左右のスクロール同期も要らない）。
    unified は従来どおり折り返さず、新旧それぞれの行番号を持つ溝を左に置く。
  - 文脈行は左右に同じ行を出す。連続する削除行・追加行のかたまりは、**上から1対1**で
    左右に並べ（`toSplitRows`）、相手の無い側は淡色の空欄にする。似た行同士を探して
    対応づけることはしない。
- **行内の差分は単語単位**（両方の表示で付ける、`withInlineChanges`）。上の1対1で
  対になった削除行・追加行の間で、単語の LCS をとって変更部分だけ濃く塗る。
  - 単語の区切りは `Intl.Segmenter`（`granularity: 'word'`）。空白で区切らない日本語も
    辞書で単語に分かれる（「火曜日」→「水曜日」が丸ごと1語として塗られる）。依存は増えない。
  - 共通部分が両側の文字数の半分未満の「別物の行」には付けない（ほぼ全体が塗られて
    かえって読みにくいため。行の色だけで示す）。単語数の積が 25 万を超える行も付けない。
  - 変更に挟まれた空白は変更側に寄せる（細切れに塗られないように）。
- **Markdown などを描画した結果どうしの差分は出さない**（ソースどうしの比較のみ）。
- **入力はツールコールの `diffs`（変更前後の全文）のみ**（A-3-8 で「変更」
  サイドバーの累積 `git diff` 入力は廃止したため）。全文しか無いので、
  **行単位の LCS で差分を計算する**（`diffRowsFromTexts`）。
- **変更から遠い文脈は `… N 行` に畳む**（前後3行は残す）。ファイル全文を
  持つため、畳まないと小さな変更でも全文が流れてしまう。
- **巨大ファイルでは LCS を諦める。** 共通の前後を削ってもなお行数の積が
  400万セルを超えるときは「まるごと置き換え」として描く。正確さより
  「レンダラを固めない」ことを採る。

**なぜライブラリを入れないか**: 行単位の LCS は前後の共通部分を削れば
100行程度で書ける。依存を1つ増やすより、挙動（改行の正規化、末尾改行の扱い、
畳み込みの規則）を自分で決められる方が、この UI では扱いやすい。単語単位の
差分も同じ LCS（`align`）を単語の列にかけるだけで済む。

**なぜ Side by Side を足し、既定にしたか（2026-10-07 改訂）**: 当初は「サイドバーに
入る幅でも読める」ことを理由に unified だけにしていたが、そのサイドバー（「変更」
サイドバー）は A-3-8 で廃止され、Diff の表示先はトランスクリプトから開くモーダル
だけになったので、その理由はもう成り立たない。加えて、非エンジニアやドキュメント
（コードでないもの）の見比べでは、変更前後を左右に並べる方が読みやすいことが多い。
shovel は非エンジニアにも使ってもらう前提なので、Side by Side を既定にし、unified は
設定とトグルで選べるようにした。

### N-3-6. 外部変更への追随：責務を3つに分ける（2026-09-30 更新）

「エージェントがファイルを変えたことへの対応」は、目的の違う仕事からなる。
混ぜて設計しない。

| # | 目的 | 仕組み | タイミング |
| :--- | :--- | :--- | :--- |
| **(A)** | **ツリーの表示**を実態と合わせる | `readdir`（**展開中フォルダのみ**） | ターン終了時 |
| **(B)** | **開いているファイルの内容**を実態と合わせる | ファイル再読込 | ターン終了時 |

**(C)「何が変わったかを知らせ、戻せるようにする」は無くなった**: 当初は
「変更」サイドバー（常時）がこの役目を担う想定だったが、そのサイドバー自体が
A-3-8 で完全に廃止された。「戻せるようにする」（復元）は同じ A-3-8 の判断で
shovel の安全モデルから外れており（architecture.md §6「安全モデルは3層に
なった。復元層は無い」）、代わりの仕組みは作らない。「何が変わったかを知らせる」
方はトランスクリプトのツールコール単体の diff 表示（N-3-8 の Diff ビューア）が
既に担っている——エージェントがそのターンで何をしたかはそこで見える。
ファイルツリーやファイラー側に累積した変更点の一覧を持たせることはしない。

**実装（2026-10-07）**: 「ターン終了」は renderer で `session.prompt` が返った時点
（中断・失敗を含む）とし、ウィンドウ内の簡易 pub-sub（`src/renderer/main-window/turnEnd.ts`）
で知らせる。複数タブが立て続けに終えたときは 300ms でまとめて1回にする。

- (A) ファイラーは更新ボタンと同じ `refreshAll` を呼ぶ。名前変更の入力中・読み直しの最中は
  それが終わるまで待って1回だけ読み直す。
- (B) `FileViewer` は「読み込み中」を挟まずに読み直し、内容が変わったときだけ描き直す
  （一時的な読み込み失敗では表示中の内容を消さない）。`TextFileEditor` は既存のポーリングと
  同じ同期処理を、次のポーリングを待たずに走らせる。
- chunk や `tool_call` の完了ごとには読み直さない（そこまでの即時性は要らない）。

**(A)(B) が展開中フォルダに限ってよい理由**: 画面に出ていないものは正しく保つ
必要がない。閉じているフォルダは後で開いた瞬間に `readdir` されるため、
「古い情報を表示し続ける」事故が起きない。全フォルダを常時監視すると
`node_modules` まで含めた監視になり、コストだけかかって得るものがない。
`chokidar` 等のファイル監視は常時回さない。この方針は実装して使ってみた上で
**恒久的な結論として確定した**（open-issues.md V-8、2026-09-29 解決）。

**開いているファイルが削除された場合**: 黙って古い内容を表示し続けるのが最悪。
「このファイルは削除されました」と明示するに留める。「変更」サイドバー廃止
（A-3-8）に伴い、shovel 側の復元導線は案内しない。git 管理下のプロジェクトなら、
復元は使い手が普段使っている git で行える（`flows.md` §7 と整合）。

### ~~N-3-7. 「変更」サイドバーの情報源：二段構え~~ ❌ 廃止（A-3-8）

「変更」サイドバー自体を A-3-8 で廃止したため、ここで設計した `git status`
との突き合わせ（② の情報源）は無くなった。

**生き残る部分**: ACP の `tool_call`（`locations` / `diffs`）は
**トランスクリプトのツールカード単体の diff 表示**（N-3-8「Diff ビューア」の
`TextDiffView`）に使い続ける。`tool_call` から状態を復元しない、という
設計規則も同様に有効（そもそも復元機能自体が無くなったため、より単純に
「`tool_call` は表示にしか使わない」で足りる）。

<details>
<summary>廃止前の内容（履歴として保持）</summary>

**決定**

| 情報源 | 役割 | タイミング | 保持するもの |
| :--- | :--- | :--- | :--- |
| **① ACP の `tool_call`**（`locations` / `diffs`） | どのファイルが触られたか | ターン中・リアルタイム | **パスの集合のみ** |
| **② `git status`** | 実際に何が変わっているか | ターン終了時に突き合わせ | HEAD との差分 |

**最重要の設計規則: `tool_call` から復元は一切しない。**

- `tool_call` は**パスの集合**としてのみ使う。同じファイルが1ターンに何度
  変更されても、集合に冪等にマークが付くだけで、**世代も内容も保持しない**。
- 復元は常に `git restore <path>`。**中間状態を一切辿らず HEAD へ一発で戻る**。
- `tool_call` に内容や世代を持たせると「正しく復元できない」破損が現実になる。
  中間状態を追わないことが安全性の源。

**なぜ二段構えが必要か（片方だけでは穴が残る）**

- ① だけ → エージェントの**申告漏れ**を拾えない。
- ② だけ → **`.gitignore` 対象**が漏れる。**非 git プロジェクト**で動かない。
  ターン中のリアルタイム表示ができない。

② は確実性の面で**最後の砦**であり、① はリアルタイム性と非 git 対応を担う。

**同じ `diffs` でも用途が2つある**

- **トランスクリプトのツールカード** → その操作**単体**の diff（`tool_call` の
  `diffs`）。「AI が今何をしたか」
- **「変更」サイドバー** → **累積**の diff（`git diff`）。「結局どうなっているか」

**非 git プロジェクトでの振る舞い**

- 変更されたファイルの**一覧は出る**（① から分かるため）。
- **「元に戻す」ボタンは出ない**（戻す手段が無いため）。

A-3-5「git を初期化しない選択をしたら回復機能を失うだけ」と整合する。
機能ごと消すのではなく、ボタンだけ消す。

</details>

## G-1. チャット画面とウィンドウ / タブ構造

### G-1-1. ウィンドウ ＝ プロジェクト、タブ ＝ セッション

**決定**

```
Electron main プロセス（1つ）
├── Window A ＝ プロジェクト X
│    ├── タブ1 ＝ セッション a ── ACP 接続 ── sbx exec プロセス
│    └── タブ2 ＝ セッション b ── ACP 接続 ── sbx exec プロセス
└── Window B ＝ プロジェクト Y
     └── タブ1 ＝ セッション c ── ACP 接続 ── sbx exec プロセス
```

- **1 ウィンドウ = 1 プロジェクト。** `app.requestSingleInstanceLock()` で
  二重起動を捕まえ、2回目の起動要求は既存 main に転送して新しい
  `BrowserWindow` を開く（VS Code と同じモデル）。
- **1 タブ = 1 セッション = 1 ACP 接続 = 1 `sbx exec` プロセス**。
- **タブを閉じることがセッションのプロセスを終わらせる。**
  「切断」という操作は設けない。

**理由**

- **並行作業が中心的なユースケース。** エージェントの調査は長時間かかり、
  同じプロジェクトで別件を並行して調べる頻度が高い。単一セッションでは潰れる。
- 複数インスタンス起動ではなく単一インスタンス＋複数ウィンドウを採る理由:
  設定ファイルへの書き込みが1プロセスに集約されて競合せず、子プロセスを
  main が一元管理できるため**診断情報も一箇所に集まる**（N-2-6）。
  Electron ランタイムも1つで済む。
- 「プロジェクト切り替え時に前の ACP 接続を落とすか保持するか」という問題は、
  **切り替えないことで消滅する**。

### G-1-2. セッションを開く操作は「リンク」として振る舞う

**決定**: セッション履歴サイドバーの各行をリンクのように扱う。

| 操作 | 結果 |
| :--- | :--- |
| セッション名をクリック | **現在のタブ**で開く |
| 行の右端のアイコン | **別タブ**で開く |
| 右クリック（コンテキストメニュー） | 別タブで開く / 名前変更 / 削除 |

ブラウザのリンク操作と同じ操作感であり、非エンジニアの学習コストがゼロ。

### G-1-3. セッションの開始方法は2種類

**決定**

| 操作 | 接続 | 意味 |
| :--- | :--- | :--- |
| **タブ列の `+`** | **新しい接続を確立**（新しい `sbx exec` プロセス） | 別件を並行して始める |
| **タブ内コンテンツ上部のリフレッシュマーク**（円弧の矢印） | **今の接続を再利用**して `session/new` | このタブをリフレッシュする |

**理由**: 接続の確立は高価（`sbx exec` のプロセス起動と `npx` による ACP
アダプタの取得。`initialize` に 180 秒のアイドルタイムアウトを
設けているほど）。**可能な限り接続を再利用したい**ため、
「新しい会話を始める」ための軽い経路を別に用意する。

どちらが多く使われるかは未知数であり、実利用で観察する。

### G-1-3b. タブ数の上限は 10

**決定**: 同時に開けるタブは**最大 10**。

**理由**: タブ切り替えのショートカットを「修飾キー + 0〜9」に割り当てるため。
機能的な制限ではなく、**キーボード操作の設計から導かれた数**。
副次的に、各タブが抱える Node プロセス（ACP アダプタ）によるメモリ圧迫も抑えられる。

### G-1-4. 背景タブの通知

| 状態 | 表示 |
| :--- | :--- |
| **権限要求待ち** | アイコンにバッジ。**前面にないタブにだけ**出す（前面のタブは承認カード自体が見えている）。答えるか、自動許可されるか、ターンが終われば消える |
| **ターン実行中** | アイコンの不透明度が約1秒周期で 1.0 ↔ 0.35 に脈動 |
| **ターン終了** | **通知しない。** どのタブもターンを終えるため、通知するとタブ列全体が光り続ける |

### G-1-5. コンテキスト添付

**決定**

- **選択範囲の添付は実装しない**。
- **アクティブファイルの自動添付は設定項目とし、既定は off。**
- 添付状態は**必ずチップで可視化**し、✖ で1クリック除外できる。
  チップにはパスのみを表示し、内容のプレビューは出さない。

**理由**: 意図しないファイルが外部 LLM に
送られることを防ぐため、自動収集は明示的なオプトインとし、送信対象は
常に UI 上で完全に可視化する。

#### G-1-5a. 添付は `resource_link`（パスのみ）で送る（2026-10-01 決定）

**決定**: 添付ファイルは中身を読まず、`resource_link`
（`file://{sandboxPath}/{relPath}`）の ContentBlock として送る。エージェントは
リンクを見て、サンドボックス内で自分の Read ツールを使ってファイルを読む。

**前提**: shovel は Docker Sandboxes（プロジェクトディレクトリが双方向マウントされ、
`sandboxPath` は実測値。N-6a）と claude-agent-acp に対象を限定しているので、
エージェントがサンドボックス内から同じファイルを読める。

**理由**

- ACP では `resource_link` はすべてのエージェントが受け付ける基本形で、
  `resource` は `promptCapabilities.embeddedContext` を宣言したエージェントに
  しか送れない。プロトコル上もリンクのほうが安全。
- ホスト側でサイズ上限・文字コード・バイナリ判定・トークン量を気にしなくてよい。
- エージェントが実際にファイルを読んだかが、トランスクリプトの Read ツール
  コールとして見える（中身を送る方式では「送ったつもり」で終わる）。
- shovel がファイルの中身を仲介しないので、architecture.md §6 の
  「shovel はファイル操作を仲介しない」という前提とも揃う。

**受け入れた制約**

- **読まれる保証はない。** claude-agent-acp は `resource_link` を
  `[@name](file://…)` という Markdown のメンションに変換してモデルへ渡すだけで、
  CLI のような `@` 参照の自動展開はしない。読むかどうかはモデルが決める。
- **大きなファイルは分割して読まれる。** Claude Code の Read には行数・
  トークンの上限があり、超えるとエージェントが offset/limit や grep で
  部分的に読む。壊れはしないが、全文が一度に読まれるとは限らない。
- **送信時点の内容は記録に残らない。** スナップショットに残るのはパスだけ。
  エージェントの Read 結果は会話の中に残る。
- **ログに出る Base64 は shovel が送ったものではない。** 画像・PDF を Read
  すると、Claude Code は Base64 の image ブロックを返し、claude-agent-acp が
  それを `tool_call_update` の `rawOutput` に載せて送り返してくる
  （サンドボックス → ホスト方向）。shovel は `rawOutput` を使わない。

**付随する実装**

- 送信前に、開いている Markdown エディタの未保存編集をディスクへ書き出し、
  **書き込みの完了を待ってから** `session/prompt` を送る（flows.md §4、
  `editorRegistry.ts`）。エージェントはディスク上のファイルを読むため、
  autosave のデバウンス（600ms）内の編集を送信前に確定させる必要がある。
- `session/load` の replay では、添付は `resource_link` のまま返るとは限らず、
  claude-agent-acp は上記のメンション文字列として流し直す。翻訳層
  （`translate.ts` の `appendUserChunk`）で `resource_link`・`resource`・
  メンション文字列のいずれもライブ送信時と同じチップに戻し、本文からは
  取り除く。プロジェクト外を指すものはチップにできないので本文に残す。
- URI の組み立て方（パーセントエンコードの有無）は open-issues.md V-20 で
  実機確認待ち。

### G-1-6. プロジェクト操作の UI

**決定**: Header のドロップダウン（軽い切り替え）と、
独立したプロジェクトマネージャウィンドウ（作成・管理）の二段構え。

```
Header の「プロジェクト名 ▾」をクリック
  ├─ 最近のプロジェクト（数件）        ← 軽い切り替え
  ├─ ＋ 新しいプロジェクト…            → マネージャの作成フローへ
  └─ すべてのプロジェクト…             → プロジェクトマネージャウィンドウ

アプリ起動時、開くプロジェクトが決まっていなければ
  → プロジェクトマネージャウィンドウ
```

**プロジェクトは常に新しいウィンドウで開く。すでに開いていれば、
そのウィンドウを前面に出す。** 「現在のウィンドウで開く」という選択肢は
設けない（ウィンドウ＝プロジェクトという不変条件を守るため）。
これにより「走行中のターンを中断しますか」という確認も不要になる。

**理由**

- **ウィンドウ＝プロジェクトにした時点で、プロジェクト一覧の性格が変わった。**
  常用のスイッチャーではなく、**ランチャー／管理画面**になった。
  日常の切り替えは OS のウィンドウ操作（`Cmd+\`` / `Alt+Tab`）が担う。
- プロジェクトに必要な操作は12個あり（開く・切り替え・2種類の作成フロー・
  既存サンドボックスのインポート・名前変更・削除・停止・診断・認証設定・
  状態表示）、**サイドバーの幅に収まらない**。
- 構造上の問題も解消する。サイドバーの他の項目（チャット履歴・ファイラー・
  変更）は**すべて「このプロジェクトの中身」**を見るものであり、
  プロジェクト一覧だけが「外」を見ていて異物だった。
- Header にプロジェクト名を置く要求書の構成に、切り替えを素直に足せる
  （Slack / Linear / GitHub Desktop と同じパターン）。
- 起動時の入口が明確になる。非エンジニアには「最初に見る画面」があることが重要。

### G-1-7. サイドバーの構成（要求書からの変更）

**決定**

| | 要求書 | shovel |
| :--- | :--- | :--- |
| 上付き | プロジェクト一覧 / チャット履歴（既定）/ ファイラー | **チャット履歴（既定）/ ファイラー / 変更** |
| 下付き | コマンド実行 | コマンド実行 |

- 「プロジェクト一覧」を外す（G-1-6 へ移動）。
- 「変更」を追加する（A-3-7）。
- サイドコンテンツが排他ではなく左から順に並ぶこと、既定サイズがあり可変で
  サイズが記憶されることは要求書のまま。

## N-5. 編集の競合：ロックせず、autosave と競合コピーで解く

**決定**

1. **Markdown エディタは autosave**（入力が止まって数百ms〜1秒でディスクへ。
   連続入力に備えて最大待ち時間も設ける）。**UI に「保存」ボタンを出さない。**
2. **プロンプト送信時に明示的にフラッシュする**（autosave のデバウンス待ちを飛ばす）。
3. 開いているファイルが外部で変わったとき:
   - 未保存の編集が**ない** → 黙って再読込。
   - 未保存の編集が**ある** → **ユーザーの版を別名で保存**してからエディタを
     最新に更新し、通知バーで知らせる。
     - 命名: **`<名前>.conflict-<YYYYMMDD-HHmmss>.<拡張子>`**
       （言語非依存・時刻順にソート可能・衝突しない。「競合コピー」のような
       日本語をファイル名に入れると英語 UI との整合が崩れる）
     - 通知バー: 「AI がこのファイルを変更したため、あなたの編集を
       `spec.conflict-20260914-153012.md` に保存しました ［開く］」
4. **ロック・3択の競合ダイアログ・Diff 表示はいずれも作らない。**

**理由**

- **「ターン中はワークスペースを読み取り専用にする」方式は
  タブ方式と両立しない。** shovel は同一プロジェクトで最大10タブが並行して
  ターンを走らせるため、「どれか1つが動いていればロック」では**ほとんど常に
  ロックされた状態**になり、「並行して別件を調査する」という中心的
  ユースケースと衝突する。
- **ターン開始時に未保存バッファをディスクへフラッシュする必要がある。** エージェントは IDE のバッファではなく**ディスクを読む**ため、
  未保存のままプロンプトを送ると「さっき直したのに AI が古い内容で答える」
  という原因の分かりにくい事故になる。
- **autosave にすると「未保存」という状態がほぼ消え、問題の大半が消滅する。**
  非エンジニアにとって「保存」という概念自体が馴染まない
  （Obsidian / Notion / Apple のメモはいずれも autosave）。
- 競合コピー方式は**何も失われない**。Dropbox / iCloud で広く知られた挙動であり、
  Diff 表示（JetBrains のやり方）より軽く、3択ダイアログのような判断も
  ユーザーに求めない。
- **ターン実行中の編集ロックは対応しない。これは最終決定である。** 上記の
  タブ並行という理由に加え、当初は「万一の取り違えは④「変更」サイドバー＋
  git で回復できる（A-3-7）」ことも理由の一つだったが、その安全網自体が
  A-3-8 で廃止された。それでもロックを採用しないのは、競合コピー方式が
  そもそも**取り違えても何も失わない**ため、別の回復手段を必要としないから
  である。

**検討したが採用しなかった案: memfs + unionfs**

**この問題には原理的に効かない。** memfs / unionfs は「Node プロセス内の `fs`
モジュールを差し替える」JavaScript レベルの仕組みであり、実際のファイル
システムを作るものではない。エージェントは**別プロセス**かつ**コンテナの中**から
本物の syscall でバインドマウントを読み書きするため、ホストの Node プロセス内に
張った仮想レイヤーは一切見えない。競合しているのは「1プロセス内の2つの
コードパス」ではなく「別マシン相当の2プロセス」である。

（memfs + unionfs が有効なのは、テストでの `fs` 差し替え、バンドラの仮想ファイル、
ブラウザ内実行環境などの用途。）

## G-3. オンボーディングとプロジェクト作成フロー

ここまでの決定が合流する画面。N-2-5（エージェント対応表）、A-3-5（`git init`）、
N-2-7b（認証）、N-2-1（サンドボックス名）、N-2-2（既存サンドボックス）、
N-2-6（`sbx diagnose`）が集まる。

### G-3-1. 作成フローは3種類

**フロー1: 新規ディレクトリ作成（推奨・既定）**

```
1. エージェントを選ぶ              ← 対応表の verified のみ（N-2-5）
2. プロジェクト名を入力             ← displayName。日本語可
3. ベースディレクトリを選択
4. プロジェクトパスを確認           ← 編集可（要求書通り）
   ─── 詳細（折りたたみ）────────────────────
   サンドボックス名                 ← 自動導出。編集可（N-2-1）
   ☑ git で変更を戻せるようにする   ← 既定 ON（A-3-5）
5. 作成
```

**フロー2: 既存ディレクトリ追加**

```
1. プロジェクトパスを選択
2. エージェントを選ぶ              ← ★ 要求書に無い。記載漏れのため追加
3. プロジェクト名を確認             ← 既定はディレクトリ名
4. 警告と同意
   「このディレクトリ内のファイルは、隠しファイルを含めすべて AI に参照されます」
   ＋ git リポジトリでない場合のみ:
   「☑ git で変更を戻せるようにする（オフにすると AI の変更を元に戻せません）」
5. 作成
```

**フロー3: 既存サンドボックスから追加（新設・N-2-2）**

`sbx ls --json` にあって shovel の一覧に無いものを提示する。
**エージェントもパスも `sbx` が知っている**ため、聞くのは表示名だけ。

```
1. 一覧から選ぶ    ← name / agent / workspaces / status が sbx から取れる
2. 表示名を確認    ← 既定はサンドボックス名
3. 追加
```

**要求書からの変更点**: 要求書の2つのフローを比べると、
**「既存ディレクトリ追加」にだけエージェント選択が無い**。どちらも
`sbx create <AGENT> <PATH>` を実行する以上エージェントは必須であり、
記載漏れと判断して追加する。

### G-3-2. `sbx create` は作成フローの中で完了まで待つ

**決定**: 作成フローの最後で `sbx create` を実行し、**完了まで待つ**。
進捗表示を必ず出す。

**理由**: 初回はコンテナイメージの取得で数分かかる可能性がある。
登録だけ先に済ませる方式だと、**「登録は成功したのに後で開いたら動かない」**
という、非エンジニアには原因の分からない体験になる。作成フローの中なら
「今何をしているか」を説明しながら待たせられる。

### G-3-3. 初回起動

```
1. 前提チェック    sbx diagnose を実行
                  → 失敗なら出力をそのまま見せ、対処を案内（A-2 / N-2-6）
                  → sbx login が必要なら「ターミナルを開いてログイン」へ誘導
2. プロジェクトマネージャへ
                  空状態では「最初のプロジェクトを作る」を大きく出す
```

**エージェントの認証を初回起動時に先回りして聞かない。**
`claude auth status --json` で状態が分かるため、**必要になった時点で
必要な人にだけ**出せばよい（プロジェクト作成の最後、または接続前）。
すでにログイン済みの人には何も聞かない。

これは「前提条件を最小化する」「使い方を強制しない」という設計指針の具体化であり、
**うまくいっている人には何も聞かない**という原則に従う。

## N-4. コマンド実行：TTY なしの対話コンソール ＋ TTY モード ＋ OS ターミナルへの逃げ道

**決定**

- **`sbx exec -i <sandbox> <command>`** を使う。**`-t` は付けない**。
  stdin は開くので `[Y/n]` のような対話プロンプトには答えられる。
- UI は「ログ表示 ＋ 入力欄 ＋ 中断ボタン」。
- カーソルで選ぶ・スペースで選ぶような TUI のために、実行ごとに切り替えられる
  **TTY モード**を持つ（2026-10-08 追加。下の「TTY モード」を参照）。
  TTY モードの表示にだけ xterm.js を使う。
- 作業ディレクトリは `-w` でプロジェクトのワークスペースを既定にする。
- 出力は**ストリーム表示**。**ANSI エスケープは除去**し、`\r` で上書きされる
  進捗行は1行として畳む。**出力行数に上限**を設け、
  超えた分は古い行から捨てる。
- **履歴はプロジェクト単位**（プロジェクトごとに使うコマンドが違い、
  混ざると候補が汚れるため）。
- 「プロジェクトの詳細」に **OS のターミナルアプリを開く**導線を1つ置く
  （`sbx exec -it <sandbox> /bin/bash -l` を渡す）。

**履歴の持ち方（2026-09-30 決定）**

- **保存するのはコマンド文字列のみ。** 出力ログ・終了コード・実行時刻などは
  保存しない。理由は2つ：
  1. コマンドの出力にはシークレットやトークンが混ざりうる（`env` の中身を
     表示するコマンドなど）。これをホスト側の `electron-store` に永続化する
     のは「シークレットはサンドボックス内、ホストに書き出さない」という
     方針と衝突する。
  2. 出力を見返したいだけなら、ドロワー自体がタブを閉じるまで表示され
     続けているので、それで足りる。「作らずに済むものは作らない」。
- **同じコマンドを重複して残さない（MRU 方式）。** 同じコマンド文字列を再度
  実行したら、履歴内の古いエントリを削除してから最新の1件として積み直す。
  結果として履歴には各コマンド文字列が常に1つだけ存在し、「最近使った順」を
  保つ（`zsh` の `HIST_IGNORE_ALL_DUPS` やブラウザの検索履歴と同じ挙動）。
- **保持件数は最新20件。** 超えた分は古い方から捨てる。コマンド文字列のみ・
  MRU 方式で肥大化の心配は薄いが、一覧・補完に使う想定であれば無制限に積む
  よりも直近のよく使うものだけに絞った方が実用的、という感覚値での判断。
- **UI は「↑キーでの呼び戻し」と「履歴一覧パネル」を併用する。** shovel は
  非エンジニアも使う想定であり、シェルの↑キーだけでは発見されにくいため、
  ドロワー内に直近20件を一覧表示するパネルも持たせ、どちらからでも同じ履歴に
  アクセスできるようにする。
- **選んでも即実行しない。入力欄に差し込むだけ。** ↑キー・一覧クリックの
  どちらも「そのコマンド文字列を入力欄に呼び戻す」動作に統一し、実行は
  ユーザーが改めて Enter／実行ボタンを押すまで行わない。過去の破壊的な
  コマンド（`rm` 系など）を誤って一覧からクリックしてそのまま実行してしまう
  事故を防ぐため。A（↑キー）と B（一覧）を同じ着地点に揃えることで、実装も
  シンプルになる。

**ピン留め（2026-10-03 決定）**

- 履歴の任意のコマンドを**ピン留め**でき、ピン留めしたものは20件の押し出しの
  対象外になる。よく使うコマンドが、他のコマンドを何度か実行しただけで履歴から
  消えてしまうのを防ぐため。
- **上限は10件**（特に根拠はない感覚値。無制限にはしない）。上限に達したら
  ピン留めボタンを無効にする。
- 保存は `commandHistory` とは別キー（`pinnedCommands`、プロジェクト単位）。
  既存の履歴データの形式を変えずに済む。ピン留めと通常履歴は重複させない
  （ピン留めすると通常履歴から外れる）。
- **ピン留め中のコマンドを再実行しても位置は動かさない**（通常履歴にも出さない）。
  並びはユーザーがピン留めした順のまま固定する。
- **ピン留め中の行には×を出さず、外す操作だけ**を置く。外したコマンドは
  削除せず、通常履歴の先頭に戻す（消したければそこから×で消す）。
- 一覧ではピン留めを上部にまとめ、区切り線の下に通常履歴を並べる。
  **↑↓キーは通常履歴だけを辿る**（ピン留めを混ぜると直近の履歴に戻りにくく
  なるため。ピン留めは一覧から選ぶ）。

**TTY の有無が境界であり、stdin の有無ではない**

| | A: 1shot（stdin なし） | **B: `-i` のみ（採用・既定）** | C: ホストに PTY | **D: サンドボックス内に PTY（採用・TTY モード）** |
| :--- | :--- | :--- | :--- | :--- |
| `[Y/n]` 等の対話 | ❌ 固まる | ✅ 答えられる | ✅ | ✅ |
| カーソル選択の TUI / `vim` / `top` | ❌ | ❌ | ✅ | ✅ |
| ネイティブモジュール | 不要 | **不要** | 🔴 `node-pty` が必要 | **不要** |
| UI | ログ表示 | ログ表示＋入力欄 | xterm.js | xterm.js |
| サンドボックス側の前提 | なし | なし | なし | `python3` |

**C を採らない理由**: `node-pty` は C++ のネイティブモジュールであり、
**Electron のバージョン・OS・CPU アーキテクチャごとにビルドが必要**になる。
`electron-rebuild` と CI のビルドマトリクスが増え、さらに **macOS の
コード署名ではネイティブモジュールも個別に署名対象**になるため、
F-3（配布と署名）の複雑さが一段上がる。
当初は「失うのは `vim` のような全画面アプリだけ」としていたが、MCP の設定や
認証などに、カーソルで選びスペースで切り替える TUI が前提のツールがあることが
分かり、D（TTY モード）を追加した。D は C と同じことを、PTY をホストではなく
サンドボックスの中で作ることで、ネイティブモジュールなしで実現する。

**TTY モード（2026-10-08 決定）**

背景: カーソルで選ぶ・スペースで選ぶ UI は、標準入力に行を送るだけでは動かない。
ツールは①`isatty()` で端末かどうかを調べ、②端末を raw モードにして1キーずつ
（矢印キーは `ESC [ A` / `ESC O A` のような列で）読み、③ANSI エスケープと
端末サイズ（`TIOCGWINSZ`）を使って画面を描き直す。B の `-i` のみではどれも
成り立たない。

仕組み:

- **PTY はサンドボックスの中で作る。** `sbx exec -i` で `python3` の小さな
  ラッパーを起動し、ラッパーが `pty.fork()` で PTY を作ってコマンドを動かす。
  ホストと `sbx exec` の間は B と同じパイプのままなので、ホストに PTY は要らない。
- **ラッパーはサンドボックスにファイルとして置かない。** ソースは shovel が持ち、
  base64 にして `python3 -c` の引数で渡す（英数字と `+/=` だけになるので、
  Windows の `sbx.exe` 経由でも引数のクォートで崩れない）。
- **`python3` が無いサンドボックスでは使えない。** 起動は
  `/bin/sh -c 'command -v python3 … || { echo <目印> >&2; exit 127; }; exec python3 -c "$0" "$@"'`
  の形で、`sbx exec` を1回で済ませる。判別は stderr の目印で行う（コマンド自体が
  見つからない場合も終了コードは 127 になるため、終了コードでは区別しない）。無ければ「このサンドボックスでは TTY モードを
  使えません」と表示する。`script`（util-linux）などの代替は作らない。
- ラッパーは子プロセスに `TERM=xterm-256color` を設定する（`sbx exec` の環境には
  `TERM` が無く、curses 系のアプリが `setupterm` で落ちるため）。
- **端末サイズ**: 起動時の列数・行数は引数で渡す。実行中の変更は、stdin に独自の
  制御列 `ESC ] 777 ; shovel-resize ; <列> ; <行> BEL` を混ぜて送り、ラッパーが
  それを取り除いて `TIOCSWINSZ` を発行する（カーネルが子に `SIGWINCH` を送る）。
  パイプが1本しかないため、帯域外の経路は持たない。
- **Ctrl+C** は `\x03` をそのまま送る。PTY が SIGINT に変換するので、シグナルを
  `sbx exec` 越しに送る仕組みは要らない。
- **中断ボタン**は stdin を閉じる。ラッパーが子に SIGHUP を送って終わらせる。
  それでも終わらなければ `sbx exec` のプロセスを kill する。
- 終了コードはそのまま返す。シグナルで終わったときは 128＋シグナル番号にする。

UI と保存:

- 今のドロワー（B）は**既定として残す**。実行ごとに TTY モードへ切り替えられる。
  ログの畳み込みや出力の上限など、B のほうが扱いやすい場面が多いため。
- TTY モードはドロワーの中に xterm.js の面を出す。**タブにはしない**
  （1タブ＝1セッションの対応を崩さない）。
- **出力はどこにも保存しない。** 履歴に残すのは B と同じくコマンド文字列だけ
  （「履歴の持ち方」と同じ理由。TTY モードかどうかも保存しない）。
- xterm.js は `@xterm/xterm` と `@xterm/addon-fit` だけを入れる。純 JS なので
  F-2b（ネイティブゼロ）とは衝突しない。リンクを開く・クリップボードに書く
  （OSC 52）などのアドオンは入れない。サンドボックス内のプログラムの出力から、
  ホスト側で何かが起きる経路を増やさないため。

試作で確かめたこと（開発用サンドボックス、Ubuntu 26.04 / Python 3.14。
`sbx exec` は通していない）: ホストを Node の `stdio: 'pipe'` だけにして、curses の
複数選択メニューを ↑↓・Space・Enter で操作できた。実行中のサイズ変更
（80x24 → 120x40）、Ctrl+C（終了コード 130）、stdin を閉じての中断（129）、
通常の終了コードの受け渡しも動いた。`sbx exec -i` 越しの確認と、
エージェントのテンプレートごとの `python3` の有無は open-issues.md V-22〜V-24。

**OS ターミナルへの逃げ道を置く理由**: フル機能のターミナルを自前実装せず、
**OS のターミナルを借りる**。
実装はほぼゼロで、エンジニアにはフル機能が提供される。

**安全性の位置づけ（2026-09-30 修正）**: コマンド実行は承認カード（A-3-2 の②）
を通らない。ユーザー自身が打つものだからである。守りは**①隔離**（サンドボック
ス内なのでプロジェクト外は無事）だけが担う。かつては②の代わりを④回復（「変更」
サイドバーから戻せる）が補っていたが、そのサイドバーは A-3-8 で廃止され、
復元層は無くなった（architecture.md §6：安全モデルは①隔離→②権限カード→
③ Mode の3層で、復元層は無い）。コマンド実行で何を変えるかは**ユーザー自身の
判断に委ねる**——エージェントの操作に許可を求めるのとは別に、ユーザー自身が
明示的に打つコマンドにまで shovel が介入する理由は無い。要求書がこれを
下付きメニューに置いているのは妥当で、使わない人は開かない。

## N-6a. パスの変換：`sandboxPath` を実測して持つ

**決定**: `Project` に `sandboxPath` を追加し、**サンドボックス作成直後に
`sbx exec <name> pwd` で実測して保存する**。規則を推測しない。

```ts
Project {
  hostPath:    "/Users/tsuty/work/tool"   // または C:\Users\tsuty\work\tool
  sandboxPath: "/Users/tsuty/work/tool"   // または /c/Users/tsuty/work/tool
}
```

変換は「ワークスペースルートを起点にした相対パス」で行うため、規則が
何であれ成立する。**変換処理は1箇所に閉じ込める。**

**なぜ必要か: 3種類のパスが混ざる**

| 使う場面 | どちら側のパスか |
| :--- | :--- |
| ACP の `session/new` に渡す `cwd` | **サンドボックス内** |
| `tool_call` の `locations` / `diffs`（エージェントの報告） | **サンドボックス内** |
| ファイラー、エディタ、`shell.openPath`、`shell.trashItem` | **ホスト** |
| `sbx ls --json` の `workspaces` | **ホスト**（実出力で確認済み） |

**実測結果（2026-09-14）**

| | ホスト（`sbx ls --json` の `workspaces`） | サンドボックス内（`pwd`） |
| :--- | :--- | :--- |
| macOS | `/Users/tsuty/workspace/github.com/tsuty/shovel` | **同一** |
| Windows | `C:\Users\tutty\workspace\shovel` | `/c/Users/tutty/workspace/shovel` |

Windows の変換規則は **MSYS / Git Bash 形式**（WSL の `/mnt/c/...` ではない）。

- ドライブレター `C:` → `/c`（**小文字**）
- `\` → `/`

**規則が判明しても `sbx exec <name> pwd` による実測は続ける。** 規則は
`sbx` の実装詳細であって契約ではなく、ドライブ以外のマウント（UNC パス、
ネットワークドライブ）や将来の変更で崩れうる。実測した値を保存し、
規則は「値が妥当かの検算」にのみ使う。

**Windows 固有の追加考慮**

- **パスの大文字小文字**: Windows のホストパスは case-insensitive だが、
  サンドボックス内は Linux で case-sensitive。`sbx ls --json` の `workspaces` と
  `Project.hostPath` を照合する際は、**Windows でのみ case-insensitive に
  正規化**する必要がある。
- **セパレータ**: 相対パスを計算するときに `\` ↔ `/` の変換が要る。
  変換処理を1箇所に閉じ込める理由がここにもある。

**shovel は Windows をサポート OS に挙げている**ため、ホストとサンドボックスのパスが
同一であるとは仮定せず、明示的に変換する。

## F-1. プロセス構成と IPC

**決定**

```
main プロセス（1つ）
├─ ACP クライアント（@agentclientprotocol/sdk）  ← 子プロセスを起動するため main
├─ sbx CLI の実行（create / ls / rm / stop / exec / secret / diagnose）
├─ ファイルシステム操作（ツリー、読み書き、trashItem、openPath）
├─ git の実行（sbx exec 経由）
├─ 設定とスナップショットの永続化
├─ ACP トラフィックログ
└─ ウィンドウ管理

preload
└─ contextBridge で型付き API を公開

renderer（ウィンドウごと）
├─ React UI
├─ トランスクリプト描画（N-1）
├─ Markdown（react-markdown + remark-gfm + shiki）
└─ ファイルツリー（react-arborist）
```

- **IPC の契約は N-1 の `TranscriptEvent` / `TranscriptAction` を軸にする。**
- main は `sessionId → webContents` のマップを持ち、**イベントを `sessionId` で
  ルーティングする**（1つの main が複数ウィンドウ × 最大10タブの接続を持つため）。
- `contextIsolation: true` / `nodeIntegration: false` / CSP /
  `will-navigate` と `setWindowOpenHandler` を塞ぐ（N-1 で決定済み）。

## F-1b. renderer は `file://` ではなく `app://` で読み込む（2026-10-01 決定）

**決定**: ビルド済みの renderer（`out/renderer`）は `loadFile`（`file://`）で読まず、
独自スキーム `app://renderer/...` で読む。main が `protocol.handle` でパスを
`out/renderer` 配下に限って解決し、`fs` で読んで返す
（`src/main/windows/rendererProtocol.ts`）。開発時は従来どおり Vite の開発サーバー。

**理由**: Electron 44 では、`file://` から多数のモジュールを同時に動的 import すると
一部が `net::ERR_FAILED` で失敗する（Electron 33 では起きない。破壊的変更の一覧にも
無い）。shiki の言語定義や Mermaid の図のチャンクが読めず、ハイライトと図が壊れた。
Chromium の `file://` ローダーの問題で、`app://` でも中身を `net.fetch(file://...)` で
取ると同じく失敗する。`fs` で読んで返すと起きない。

- `app://` は `standard` / `secure` で登録するので、CSP の `'self'` と
  `will-navigate` の同一 origin 判定はそのまま効く。
- **採らなかった案**: shiki の言語読み込みを直列化する（Mermaid の図は内部で
  多数のチャンクを静的 import するので直せない）。

## F-2. 永続化

**決定**

| 保存するもの | 保存先 |
| :--- | :--- |
| プロジェクト一覧、設定、ウィンドウ状態、サイドバー幅 | **`electron-store`**（JSON） |
| セッションのスナップショット | **個別 JSON ファイル**（`{sessionId}.json`、アトミック move、`schemaVersion`） |
| セッション名の上書き（ACP に rename が無いため） | `electron-store` |
| コマンド履歴（プロジェクト単位） | `electron-store` |

すべて `app.getPath('userData')` 配下。スナップショットは
**プロジェクトツリーの外**（C-1 / C-2）。

**SQLite（`better-sqlite3`）は使わない。**

## F-2b. ネイティブモジュールをゼロにする

**決定**: shovel は**ネイティブモジュールを一切使わない**。

- `node-pty` を使わない（N-4。TTY が要る場面は、PTY をサンドボックス内で作って対応する）
- `better-sqlite3` を使わない（F-2 で `electron-store` を採用）

**理由**: macOS のコード署名では**ネイティブモジュールも個別に署名対象**になり、
Windows でも Electron バージョン × OS × CPU アーキテクチャごとのビルドが要る。
**ネイティブゼロなら署名は「アプリ本体1つに署名する」だけ**になり、
後から証明書を差し込むのが容易になる（F-3 に直結）。

## F-3. 配布とコード署名：今は署名せず、署名できる構成を保つ

**決定**

| 段階 | 対象 | 署名 |
| :--- | :--- | :--- |
| v0 | 作者と技術者 | 無し（README に回避手順を記載） |
| v1 | 非エンジニアを含む macOS ユーザー | **macOS のみ（Apple Developer Program $99/年）** |
| v2 | Windows も | Windows 証明書を追加 |

`electron-builder` の設定は**最初から書いておき**、証明書だけ後から入れる。

**前提の共有（署名が無いと起こること）**

| OS | 署名なしで起こること | 必要なもの | 年間費用 |
| :--- | :--- | :--- | :--- |
| macOS | Gatekeeper が「開発元を検証できません」で拒否 | Developer ID 署名 ＋ notarization | $99 |
| Windows | SmartScreen が「PC が保護されました」と警告 | Authenticode 証明書 | OV $200〜400 / EV $300〜600 |

Windows は 2023年以降、**証明書のハードウェアトークンまたは HSM 保管が必須**。
CI で自動署名するにはクラウド HSM サービス（Azure Key Vault、SSL.com eSigner 等）
が要る。

**署名が無いと非エンジニアはアプリを起動できない**ため、要求書の目標を達成する
にはいずれ必要になる。ただし設計段階で年間費用を確定させる必要はない。

## F-4. 自動更新は F-3 に従属する

## F-5. i18n（詳細は `ui.md` §13）

### G-1-8. 実装時に落としやすい項目

- 🔴 **IME 合成中の Enter で誤送信しない。** 日本語入力では変換確定の Enter と
  送信の Enter が衝突する。`compositionstart` / `compositionend` と
  `KeyboardEvent.isComposing` で判定する。**日本語話者が最初に踏む地雷。**
- **Enter = 送信 / Shift+Enter = 改行**（変更可能にする）。
- **入力欄は自動拡張**（約2行〜8行、超えたら内部スクロール）＋
  **ドラッグで高さ調整**できる。
- **送信中は Send ボタンが Stop に変わる**（別ボタンを置かない）。
  Stop は `session/cancel` を送る。
- **スラッシュコマンド補完** — 行頭の `/` で `available_commands_update` の
  候補を出す。
- ⚠️ **`configOptions` の更新規則。** `session/new` / `load` / `resume` と
  `config_option_update` が運ぶのは**全体**の状態でキャッシュを置き換えるが、
  `session/set_config_option` の応答は**部分的**（`mode` / `model` のみ）で
  キャッシュに**マージ**する。素朴に「応答で置き換える」と実装すると
  Effort などのセレクタが消える。
- **トークン使用量は `usage_update` を受け取ったときだけ表示する。**

### G-1-9. チャットの右に Markdown を添える（分割表示、2026-09-30 決定）

（2026-10-05 追記: エディタの共通化により、Mermaid / JSON / YAML / テキストも同じ方法で添えられる。
N-3-1 の再改訂を参照。以下の「Markdown」は編集できるテキストファイル全般に読み替える）

**決定**: チャットタブの右に Markdown を1つ添えて、左右に並べて表示できる
（左右の分割のみ。上下分割はしない）。

- **添え方**: Markdown タブのツールバーの「チャットの横に表示」、または
  ファイラーで Markdown ファイルを右クリック「チャットの横で開く」。添え先は
  今のタブがチャットならそのタブ、そうでなければ直前にアクティブだった
  チャットタブ。既に別の Markdown を添えていれば置き換える。
- **紐づけ**: 添えた Markdown はそのチャットタブに紐づく。別のチャットタブへ
  切り替えると、そのタブに添えた Markdown（無ければ無し）が表示される。
- **タブバーでの扱い**: 添えている間、その Markdown は独立したタブとして
  出さない（同じファイルの独立したタブがあれば閉じる。二重に並べない）。
  したがって10タブ上限にも数えない。ファイラーから同じファイルを開くと、
  添えているチャットタブが前に出る。
- **閉じ方**: 右ペイン上部の × で外す（独立したタブにも戻さず、単に閉じる）。
  **チャットタブを閉じると、添えた Markdown も一緒に閉じる**（添えている間は
  「そのチャットタブの一部」という扱いのため）。どちらの場合も編集は書き出す
  （N-3-3 追記）。↻ は同じタブのまま新しい会話を始める操作なので、添えた
  Markdown はそのまま残す。
- **エディタの表示**: 「分割」は出さず、ソースとプレビューの切り替えだけ
  （N-3-3 追記）。
- **幅**: 境界をドラッグして変えられ、幅は記憶される。チャット側は最小幅
  （320px）を保ち、場所が足りなければ Markdown 側が縮む。
- **ショートカット**: Cmd/Ctrl+数字でタブを選んだときは、選んだタブだけを表示
  する。Markdown を添えているチャットタブを選んだ場合は分割を解除し、Markdown は
  そのチャットのすぐ右の独立したタブに戻す（マウスでタブを選んだときは分割を
  保つ）。

**採らなかった案**: VS Code のように左右2つのペインがそれぞれタブを持つ方式。
実装が最も重く、非エンジニアには「どちらのペインのタブか」が分かりにくい。

### G-1-10. プロンプトの送信キー（2026-09-30 決定）

G-1-8 の「Enter = 送信 / Shift+Enter = 改行（変更可能にする）」を、設定
ダイアログの「送信キー」として実装する。選択肢は2つ:

- **Enter で送信（Shift+Enter で改行）** — 既定
- **Cmd/Ctrl+Enter で送信（Enter で改行）** — 修飾キーは macOS が Cmd、
  それ以外は Ctrl

対象は**プロンプト入力欄のみ**（コマンド実行ドロワー等には効かせない）。
IME 合成中の Enter で送信しない規則はどちらでも同じ。

### G-1-11. チャット一覧とタブのアイコン（2026-09-30 決定）

- チャット履歴パネルの「チャット」一覧には**会話（セッションタブ・履歴タブ）
  だけ**を並べ、開いたファイルのタブは出さない。
- 「チャット」一覧の行の右クリックは「名前を変更」（`square-pen`）と
  「閉じる」（`message-square-x`）。記録を消すのではなくタブを閉じるだけなので、
  「削除」とは書かない。履歴一覧の行は「名前を変更」と「削除」（`trash-2`）。
- タブバーのアイコン: セッション `bot`、履歴タブ・Read Only タブは時計
  （`clock-3`）、ファイル `file`。
- ファイラーの右クリックのアイコン: パスをコピー `link` / コンテキストに追加
  `file-plus` / 新規フォルダ `folder-plus` / 新規ファイル `file-plus-2`（サブメニュー:
  新規メモ（Markdown）`file-text` / 新規メモ（Text）`file-type` / 新規図（Mermaid）Mermaid のロゴ（ブランド色 `#FF3670`）/
  新規ページ（HTML）`file-code` /
  新規設定（JSON）`file-braces` / 新規設定（YAML）`file-cog`）/
  コピー `clipboard-copy` / 貼り付け `clipboard-paste` / 名前を変更 `square-pen` /
  削除 `trash-2` / Finder で開く `folder-open`。削除のアイコンはアプリ内で
  `trash-2` に統一する。
- タブの右クリックのアイコン: 閉じる `x` / 他のファイルを閉じる `file-x` /
  すべてのファイルを閉じる `copy-x`（G-1-12）。

### G-1-12. タブの右クリックメニュー（2026-10-02 決定）

ファイルを開きすぎたときにまとめて閉じられるよう、タブバーのタブに右クリック
メニューを付ける。

- **閉じる** — 種類を問わず ✕ と同じ。
- **他のファイルを閉じる** — 右クリックしたファイルのタブ以外の**ファイルのタブ**を
  閉じ、右クリックしたタブを前面に出す。ファイルのタブでだけ出す（チャット・履歴の
  タブでは「すべてのファイルを閉じる」と同じになるため）。
- **すべてのファイルを閉じる** — ファイルのタブをすべて閉じる。

まとめて閉じる2つは**チャット・履歴のタブを閉じない**。チャットのタブを閉じると
そのセッションのプロセスが終わり、応答中のターンも止まるため、「ファイルを
片付けたいだけ」の操作で巻き込まない。「右側のタブを閉じる」は入れない。

### G-1-13. ファイル表示の文字サイズ（2026-10-02 決定）

設定ダイアログに「ファイル表示の文字サイズ」（`editorFontSize`、11〜20px、既定 14px）を
足す。対象はファイルのビューア・Markdown エディタ（ソースとプレビュー）・差分表示。
トランスクリプトの文字サイズ（`transcriptFontSize`）とは別にする（チャットは読む、
ファイルは見比べる、と用途が違うため）。差分表示はこの 0.86 倍（既定で従来の
`text-xs` 相当）。トランスクリプト中のコードブロックは従来どおりトランスクリプトの
文字サイズに従う。

**フォント（書体）の設定は入れない。** インストール済みフォントの一覧を取る標準の
API が Electron に無く、自由入力にしても非エンジニアには扱いにくいため。

### G-1-14. ウィンドウを閉じたときのアプリの振る舞い（2026-10-03 決定）

プロジェクトのウィンドウを開くとプロジェクトマネージャは閉じる。以前は全ウィンドウが
閉じたときの終了を OS の慣習に任せていたため、macOS では最後のプロジェクトのウィンドウを
閉じると「ウィンドウ無しで常駐」になり、Dock のクリックに気付かなければ何もできなかった。

- **最後のプロジェクトのウィンドウを閉じたら、プロジェクトマネージャを開く**（全 OS）。
  プロジェクトマネージャは入口でありプロジェクト切り替えの起点なので、閉じたら入口へ戻る
  （JetBrains IDE の Welcome 画面と同じ考え方）。
- **プロジェクトマネージャを閉じて、ウィンドウが 0 個になったらアプリを終了する**（全 OS）。
  macOS の慣習（ウィンドウを閉じても常駐）からは外れるが、「ウィンドウ無しで何もできない
  状態」そのものを無くすことを優先した。
- 終了処理中（Cmd+Q など、`before-quit` 以降）はプロジェクトマネージャを開き直さない。
- macOS のアプリメニューに「プロジェクトマネージャを開く」（Cmd+Shift+O）を足す。
  ラベルは言語設定に従い、変更されたら作り直す。他の OS は既定のメニューのまま。

却下した案: 「最後のプロジェクトのウィンドウを閉じたらアプリを終了する」。別のプロジェクトへ
移るたびにアプリを起動し直すことになり、1 プロジェクト専用アプリのような振る舞いになるため。

### G-1-15. ツールチップはネイティブの `title` に任せず自前で描く（2026-10-08 決定）

**決定**: `title` 属性の説明は、OS／Chromium のネイティブのツールチップではなく、各ウィンドウのルートに
1つ置いた `TooltipLayer`（`src/renderer/shared/components/TooltipLayer.tsx`）が描く。

- JSX ではこれまでどおり `title` を書く。ホバーした時点で `title` を `data-tip` へ移し（ネイティブの
  ツールチップを出さないため）、約400ms 後に要素の下（収まらなければ上）へ出す。
  アイコンだけのボタンは、読み上げ用の名前が消えないよう同じ文を `aria-label` にも写す。
- キーボードでフォーカスしたとき（`:focus-visible`）はすぐ出す。クリックでのフォーカスでは出さない。
- クリック・キー入力・スクロール・ウィンドウからのフォーカス移動で消す。
- 説明文の改行（`\n`）はそのまま改行にする。ⓘ アイコンだけの補足は `InfoTip` を使う（`title` 付きの
  ⓘ。フォーカスできるのでキーボードでも読める）。

**理由**: ファイラーの中身検索のダイアログに置いた ⓘ の `title` が、利用者の環境で表示されなかった。
原因は特定できていないが、コンソールの ⓘ など同じ作りの説明がアプリ全体にある（約50か所）。
1つずつ部品に置き換えると書き忘れが出るので、`title` を書けば必ず出る仕組みを1か所に置いた。

**採らなかった案**:
- **`title` を使う箇所をすべてツールチップ部品に書き換える**: 箇所が多く、今後の書き忘れも防げない。
- **Tailwind の `group-hover` で CSS だけで出す**: `(hover: hover)` の環境でしか効かない
  （開発用サンドボックスの Xvfb では出なかった）。
- **Radix の Tooltip を足す**: 各箇所を書き換える点は同じで、依存も増える。

### G-1-16. 入力欄・エディタの右クリックメニュー（2026-10-17 決定）

**決定**: 編集できる場所（エディタ・プロンプト入力欄・検索欄などの入力欄）を右クリックしたら、
**OS 標準のメニュー**を出す。main がすべてのウィンドウの `webContents` の `context-menu` で出す
（`src/main/windows/editContextMenu.ts`）。編集できない場所では何も出さない（ファイラーやタブなど、
独自のメニューを持つ場所はこれまでどおり）。

- 項目: スペルミスの上なら先頭に候補（押すと置き換える。候補が無ければ「スペルの候補はありません」）、
  元に戻す・やり直す・切り取り・コピー・貼り付け・すべて選択。使えない項目は押せない。
- 文言は言語設定に合わせる（main 側の `resolveLocale`）。
- これまで Electron の既定どおり、どこを右クリックしても何も出なかった。

**理由**:
- Markdown ではスペルチェックを有効にしているのに、候補を選んで直す手段が無かった。候補は main の
  `context-menu` でしか取れない。
- エディタだけでなく、プロンプト入力欄などの右クリックもまとめて使えるようになる。
- 見た目はアプリ独自のメニュー（ファイラー・タブ）と違うが、文字の編集では OS 標準の見た目が自然。

**採らなかった案**:
- **アプリ独自のメニュー（ファイラー・タブと同じ見た目）をエディタに付ける**: スペルの候補を出せず、
  効くのもエディタだけになる（ほかの入力欄は個別に足すことになる）。

## N-2. サンドボックスのライフサイクル管理

### N-2-0. shovel はサンドボックスのライフサイクルを管理する

**決定**: 作成・削除・停止・状態監視を shovel が行う。

**理由**: 非エンジニアに「先にターミナルで `sbx create` してください」は成立しない。

**代償と、その受け止め方**

1. `sbx` CLI に密結合する → 要求書が「Docker sandboxes のみを対象とする」と
   宣言済みなので織り込み済み。
2. アプリ外での操作との整合性を引き受ける → A-3-1 の「アプリ外と共存する」
   原則に従い、**自動同期せず差分を提示する**（N-2-2）。

### N-2-1. プロジェクトのデータモデル

**決定**

```ts
Project {
  id:          UUID          // shovel が生成。displayName を変えても不変
  displayName: string        // 自由（日本語可）。UI に出る
  hostPath:    string        // ホストのディレクトリ
  sandboxName: string        // sbx の制約に従って導出＋衝突回避
  sandboxId:   UUID          // sbx が採番した id。照合に使う
  agentId:     string        // エージェント対応表のキー（N-2-5）
}
```

`access`（Read only / Read-write）は持たない。A-3-4 で概念ごと廃止した。

**理由**

- ホストのディレクトリ / サンドボックス / shovel のプロジェクトは別物であり、
  **名前の制約が異なる**。`sbx --name` が許すのは
  「letters, numbers, hyphens, periods, plus signs and minus signs only」で、
  日本語やスペースを含むプロジェクト名は使えない。
- `displayName` の変更が `sandboxName` に波及しないことが肝。要求書の
  「プロジェクトの名前変更」がサンドボックスの作り直しを伴わずに済む。
- `sandboxId` を持つのは、名前より ID の方が照合が堅牢なため
  （`sbx ls --json` が UUID を返す）。

### N-2-2. 状態の真実の所在

**決定**: **(A) shovel の設定を真実とする。** `sbx` は実行基盤として使う。
起動時に `sbx ls --json` と突き合わせ、**差分を UI に提示する。自動同期はしない。**

| 差分 | shovel の振る舞い |
| :--- | :--- |
| shovel にあって sbx に無い | 「サンドボックスがありません」＋［再作成］を提示。**設定は消さない** |
| sbx にあって shovel に無い | プロジェクト追加画面に「既存のサンドボックスから追加」として提示 |
| `workspace_missing: true` | ホストのディレクトリが消えている旨を提示 |
| `status: "stopped"` | 何もしない（開けば自動起動する。N-2-3） |

**理由**

- (B)「`sbx ls` を真実とする」は成立しない。`sbx ls --json` の返す項目は
  `name` / `id` / `agent` / `status` / `workspaces` / `workspace_missing` のみで、
  **ラベルやメタデータを保存する機構が無く**、`displayName` を置く場所がない。
- 自動で消さない・自動で足さないのは A-3-1「使い方を強制しない」の具体化。
- `workspace_missing` は **sbx 自身が検出してくれる**ため、shovel がホストの
  パスを stat する必要はない。

### N-2-3. 起動・停止の自動化

**決定**

| 操作 | 方針 |
| :--- | :--- |
| プロジェクトを開く | **「起動」という概念を UI から削除する。** `sbx exec` が停止中のサンドボックスを自動的に起動するため、ACP 接続そのものが起動を兼ねる |
| アプリ終了 | **自動停止しない。** 裏で走らせ続けたい利用者を妨げない |
| 停止・診断 | 「プロジェクトの詳細」画面に置き、常時は見せない |
| 現在の状態 | **Header に常時表示**（要求書の Header には状態表示が欠けている） |

**根拠**: `sbx exec --help` —
"Execute a command in a sandbox. **If the sandbox is stopped, it is started first.**"
`sbx` に `start` コマンドは存在しない。

### N-2-4. 削除

**決定**

- サンドボックスの削除は `sbx rm --force`（shovel は非対話なので `--force` 必須。
  確認 UI は shovel 側で出す）。
- **ホストのディレクトリ削除は shovel 自身の責任。** `sbx rm` はホストの
  ワークスペースを削除しない（"removes their containers, cleans up any Git
  worktrees, and deletes sandbox state"）。
- ディレクトリを削除する場合は `fs.rm` ではなく **Electron の
  `shell.trashItem()`（OS のゴミ箱へ移動）** を使う。取り返しがつくことが
  非エンジニア向けアプリでは決定的に重要。

### N-2-5. エージェント対応表（要求書 TODO への回答）

**決定**: サンドボックスは `shell` ではなく、**ACP エージェントに対応する sbx の
AGENT で作成する**。両者を結ぶ対応表をアプリに同梱する。

```ts
{
  id:            "claude",
  label:         "Claude",
  sbxAgent:      "claude",                                // sbx create <AGENT>
  acpPackage:    "@agentclientprotocol/claude-agent-acp",  // npx -y <pkg>
  secretService: "anthropic",                             // sbx secret set <SERVICE>
  status:        "verified"
}
```

**理由**

- `sbx create [flags] AGENT PATH [PATH...]` の AGENT は必須の位置引数であり、
  `shell` はその選択肢の1つにすぎない
  （claude / codex / copilot / cursor / docker-agent / droid / gemini / kiro /
  opencode / shell）。
- `sbx create claude` で作られた環境には**エージェント本体と認証経路が
  セットアップ済み**。`shell` で作ると、ACP アダプタは `npx` で入れられても
  その下で動く実エージェントと認証設定を自前で用意することになる。
- `secretService` が無いとオンボーディング（`sbx secret set`）が組めないため、
  対応表は3つ組である必要がある。

**shovel は検証済みのものだけを出す。** 非エンジニアにとって、選んだ
エージェントが動かないことはアプリの不具合として体験されるため。

**進め方**: まず `claude` + `claude-acp` の1組だけで作り、2組目
（`gemini` 等）で抽象化を検証する。

### N-2-5b. ACP アダプタの版：プロジェクトごとに記録し、更新はユーザーが選ぶ（2026-10-03 決定）

**問題**: `npx -y <pkg>` とバージョン無しで起動すると、`npx` はサンドボックス内の
キャッシュ（`~/.npm/_npx`）にある版をそのまま使い、レジストリを確認しない。ACP アダプタは
頻繁に版が上がるのに、サンドボックスを作り直すまで最初に入った版のまま動き続ける。

**決定**: 版を明示して起動し（`npx -y <pkg>@<version>`）、版はプロジェクトに記録する。

1. **プロジェクトマネージャを開いたとき**、ACP レジストリ
   （`https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json`）を読み、
   対応表の各エージェントの表示名（`name`）と最新版を控える（`acpRegistryEntries`）。照合キーは
   `distribution.npx.package` のパッケージ名。取得に失敗しても何もしない（ログのみ）
2. **セッションを開始したとき**、`initialize` の応答の `agentInfo.version` を
   `Project.acpVersion` に記録する。起動に使う版は `acpVersion` → 控えた最新版 →
   `latest` の順（`latest` はタグを毎回解決するので、キャッシュの古い版にはならない）
3. **プロジェクトのウィンドウを開いたとき**、控えた最新版が `acpVersion` より新しければ
   「更新する／今のバージョンのまま」を尋ねてから最初のタブを開く。「今のまま」を選んだ版は
   `skippedAcpVersion` に残し、それより新しい版が出るまでは再び尋ねない。答えずに閉じたら
   今回は今の版で開き、次回また尋ねる

**理由**

- 常に `@latest` にすると、上流の破壊的変更（例: `session/load` の replay の形）が
  ユーザーの知らないうちに入る。逆に固定すると、shovel 側が版を上げ続ける必要がある。
  プロジェクトごとに版を記録して、上げるかどうかをユーザーに選ばせるのが中間
- 版の確認はウィンドウを開く時点だけにする。開いているタブが途中で別の版に変わらないように
- 版を変えると `npx` が新しい版をサンドボックス内に入れるため、最初の接続は少し遅くなる

**表示**: プロジェクトの詳細の「エージェント」欄は、registry.json の `name` と記録した版で
`Claude Agent 0.85.1` と出す（レジストリ未取得なら対応表の `label`、版が未記録なら名前だけ）。

### N-2-6. ログ表示

**決定**: 「サンドボックスのログ表示」を「**診断情報画面**」として再定義する。

内容は以下をまとめ、**丸ごとクリップボードにコピーできる**形にする。

- `sbx diagnose` の出力（前提条件チェック。A-2 をこれに委譲する）
- ACP トラフィックログ（`{ms} {OUT|IN} {raw JSON}`）
- エージェントの `stderr`（`npx` のダウンロード進捗、起動失敗の理由）
- `sbx ls --json` の該当エントリ

**理由**

- **`sbx logs` は存在しない。** さらに `sbx ls --json` は Docker のコンテナ名も
  ID も返さないため、`docker logs` に辿る道もない。
- 非エンジニアにとって「ログを読む」は成立しない。価値があるのは
  **問題が起きたときに、誰かに見せられる情報を丸ごとコピーできること**。

### N-2-7. 認証情報のオンボーディング

**決定**

- `sbx secret set <SERVICE>` を shovel が代行する。
- **キーは子プロセスの stdin に直接書く。** `-t/--token` は使わない
  （help に "less secure: visible in shell history" と明記されている）。
- 初回起動時に `sbx secret import`（ホストの環境変数から検出）を提案する。

**判明した制約（技術では解決できない参入障壁）**

- `sbx secret set --oauth` が使えるのは **openai / global のみ**。
- Claude を使うには **Anthropic の API キー**が必要
  （Console アカウント＋クレジットカード登録＋従量課金）。
  **Claude Pro / Max のサブスクリプションは `sbx secret` 経由では使えない。**
- これは「非エンジニア含む」という目標に対する実質的な最大の障壁であり、
  オンボーディング UI で正直に説明する必要がある。

**要検証**: `sbx create claude` の環境内で Claude Code が独自の OAuth ログイン
（Claude.ai サブスクリプション）を通せるか。通せるなら障壁が大きく下がる。

### N-2-7b. 認証：shovel は認証フローを実装せず、状態確認と誘導だけを行う

**決定**

shovel は OAuth のブラウザフローも、コードの貼り付け UI も**実装しない**。
エージェント自身の認証コマンドを **OS のターミナルで開く**導線を提供し、
結果を**状態確認コマンドで検証する**だけにする。

N-4 で決めた「ターミナルは組み込まず、OS のターミナルを借りる」と同じ判断であり、
認証にも同じ解が効く。

#### 根拠となる実測（2026-09-14）

`claude auth status --json` が**機械可読な認証状態**を返す。

```jsonc
// 未ログイン
{ "loggedIn": false, "authMethod": "none", "apiProvider": "firstParty",
  "configDirectory": "/home/agent/.claude",
  "projectsDirectory": "/home/agent/.claude/projects" }

// ログイン済み
{ "loggedIn": true, "authMethod": "claude.ai", "apiProvider": "firstParty",
  "configDirectory": "/home/agent/.claude",
  "projectsDirectory": "/home/agent/.claude/projects",
  "email": "...", "orgId": "...", "orgName": "...",
  "subscriptionType": "pro" }
```

`claude auth login` のオプション:

| オプション | 意味 |
| :--- | :--- |
| `--claudeai` | **既定。Claude サブスクリプション** |
| `--console` | Anthropic Console（API 従量課金） |
| `--sso` | SSO フローを強制 |
| `--email <email>` | ログインページのメール欄を事前入力 |

#### これで覆った前提が2つある

1. **「認証状態を事前に判定できない」は誤りだった。**
   `sbx exec <name> claude auth status --json` で、接続を試みる前に分かる。
2. **「Anthropic の API キーが必須」も誤りだった。**
   `authMethod: "claude.ai"` / `subscriptionType: "pro"` が**サンドボックス内で**
   返っている（`configDirectory` が `/home/agent/.claude` であることから、
   ホストではなくコンテナ内の状態）。
   **Claude Pro / Max のサブスクリプションで動く。** Console アカウントも
   クレジットカード登録も必須ではない。N-2-7 で「最大の参入障壁」と記録した
   ものが**大幅に下がる**。さらに `--sso` があるため、企業のアカウント管理の
   要請にも応えられる。

#### 認証フロー

```
1. 接続前に確認   sbx exec <name> claude auth status --json
2. loggedIn: false なら認証画面を出す
     ├─ ［ターミナルを開いてログイン］   ← 既定・推奨
     │     OS のターミナルで sbx exec -it <name> claude auth login を実行
     │     ブラウザでの認証はターミナルとエージェントに任せる
     └─ ［API キーを使う］
           sbx secret set anthropic に値を stdin で渡す
3. ［確認］で再度 status を取得
4. loggedIn: true になったら接続へ
```

**shovel は OAuth を一切実装しない。** ブラウザの起動も、コールバックの受け取りも、
コードの貼り付けも、すべてターミナルとエージェントの責任。
これにより `sbx ports --publish` も不要になる。

#### 対応表の `auth`（N-2-5 の拡張）

```ts
auth: {
  statusCommand: ["claude", "auth", "status", "--json"],
  loggedInPath:  "loggedIn",                    // JSON のどこを見るか
  loginCommand:  ["claude", "auth", "login"],   // ターミナルで実行する
  secretService: "anthropic",                   // API キー経路（代替手段）
}
```

エージェントごとに違うのは**コマンドと JSON のパスだけ**。
前案の「UI を2種類作る（値の入力 / URL とコードの貼り付け）」は不要になり、
**UI は「ターミナルを開く」1種類**に減る。

#### `projectsDirectory` について

`/home/agent/.claude/projects` にセッションが保存されることが分かった。
`session/list` に非対応のエージェントでも、ここを直接読めば一覧を得られる
可能性がある。ただし**エージェント固有の実装詳細**なので、
ACP 経由（`session/list`）を主とし、これは最後の手段に留める。

#### L1（`sbx login`）も同じ扱い

Docker へのサインインもブラウザを伴う認証であり、それなりの頻度で再認証が要る。
**同じく OS のターミナルを開いて `sbx login` を実行してもらう。**
shovel は `sbx diagnose` で状態を検出し、誘導するだけ。

#### ログイン用ターミナルは成功したら閉じる（2026-10-08）

`sbx login` やエージェントのログインコマンドのように**終わりのあるコマンド**は、
成功（終了コード 0）したらターミナルのウィンドウを閉じる。ログイン完了後に
ターミナルが残り続けると、非エンジニアには「まだ何かが動いている」ように見えるため。
**失敗したときは閉じない**（エラー出力を読めるようにする）。

| OS | 実装 |
| :--- | :--- |
| macOS | `<cmd> && exit` を `do script` し、osascript がタブの `busy` を監視。シェルが終了していればウィンドウを閉じる。shovel が Terminal.app を起動した場合で他にウィンドウが無ければ、Terminal.app も終了する（ユーザーが元々開いていた Terminal.app は終了しない） |
| Windows | `cmd.exe /s /c "<cmd> \|\| pause"`（失敗時だけ止まる） |
| Linux | `bash -lc "<cmd> \|\| read"`（端末エミュレータはシェル終了で閉じる前提） |

「プロジェクトの詳細」から開く**対話シェル**（N-4）はユーザーが自分で `exit` するものなので対象外。

#### 認証はサンドボックス間で共有される（V-17 解決・2026-09-14）

一度もログインしていない新しいサンドボックスが、いきなり `loggedIn: true` を
返すことを確認した。**一度ログインすれば全サンドボックスで効く。**

→ **プロジェクト作成フローにログインステップを組み込まない。**
オンボーディングは「初回に一度だけ」で済む。

共有の**仕組みは不明**（`sbx secret` のプロキシ注入なのか、共有ボリュームなのか）。
**挙動だけを前提にし、仕組みには依存しない。**

#### `claude auth status --json` の読み方（重要）

フィールドの充足度が状態によって変わることを実測した。

| フィールド | 新サンドボックス（初回） | 対話後 | 元のサンドボックス |
| :--- | :--- | :--- | :--- |
| `loggedIn` | `true` | `true` | `true` |
| `authMethod` | `claude.ai` | `claude.ai` | `claude.ai` |
| `configDirectory` | **欠落** | あり | あり |
| `projectsDirectory` | **欠落** | あり | あり |
| `email` / `orgId` / `orgName` | `null` | 埋まる | 埋まる |
| `subscriptionType` | `null` | **`null` のまま** | `"pro"` |

認証情報は共有されるが、**プロフィールのローカルキャッシュは初回利用まで
埋まらない**という挙動に見える。

**設計規則**

1. **`loggedIn` だけに依存する。** 他のフィールドは**存在しない前提**で扱い、
   あれば表示に使う程度に留める。
2. **`subscriptionType` を当てにしない。** 共有経路では `null` のままなので、
   「Pro で利用中」のような表示を作らない。
3. **`configDirectory` / `projectsDirectory` も欠けうる。**
   セッション保存場所をここから取る実装にしない
   （C-1 で「最後の手段」と位置づけた判断が結果的に正しかった）。

#### `auth status` と接続エラーの役割分担

新品のサンドボックスがいきなり `loggedIn: true` を返すということは、
この値は**「使えるはず」という申告**であって、実際に API が通る保証ではない。
トークンの期限切れなどで嘘になりうる。

> **`auth status` は「無駄な接続試行を避けるための高速な事前チェック」。
> 真実は接続時の認証エラー。** 両方から同じ認証画面に入る。

`auth status` だけに頼ると、期限切れのときに原因不明の接続失敗になる。
接続エラーだけに頼ると、未認証の人が毎回失敗を見てから案内される。
**両方持つ。**

#### レイヤーの分離（参考）

| レイヤー | 何の認証か | コマンド | shovel の役割 | UI 上の場所 |
| :--- | :--- | :--- | :--- | :--- |
| **L1** | Docker / sbx そのもの | `sbx login` | 前提条件。検出して案内。代行の可否は要調査 | 初回起動の前提チェック |
| **L2** | エージェントの LLM API | `sbx secret set <service>` | 対応表に方式を持ち代行する | プロジェクト作成フロー |
| **L3** | ACP アダプタ | ACP の `authenticate` | `authMethods` の申告から組み立てる | L2 と同じ |

L1 は「アプリが動くための前提」、L2/L3 は「エージェントが働くための前提」で
**性質が違うため、UI 上も別の場所に置く**。

**ACP の `authenticate` を使う可能性**

`authMethods` を使えば、**エージェントごとの認証方式を shovel がハードコード
せず、アダプタ自身の申告から組み立てられる**。「エージェント × 認証方式の
パターンが多い」という問題に対するプロトコルレベルの答えになりうる。→ V-10。

**企業でのアカウント管理の観点**: API キーは個人に紐づき組織が管理しにくいため、
OAuth / SSO の方が実運用では主流になりうる。`claude auth login --sso` が
存在するため、この要請には**エージェント側の機能で応えられる**。
shovel は方式を選ばせず、ターミナルへ誘導するだけでよい。

**検討したが不要になった案**

- ~~URL を開いてコードを貼る UI~~ → ターミナルに任せるため不要
- ~~`sbx secret set --oauth`~~ → openai のみ対応であり、かつエージェント自身の
  OAuth が使えるため不要
- ~~認証のための `sbx ports --publish`~~ → ローカルコールバックを shovel が
  受ける必要が無くなったため不要


### N-2-8. 拒否された通信の表示と許可（2026-10-15 決定）

**決定**: プロジェクトの詳細に「ネットワーク」欄を設け、`sbx policy log` で
**拒否された通信の宛先**を並べる。宛先ごとに「許可」か「無視」を選べる。

- **取得**: `sbx policy log <sandbox> --type network --json` の `blocked` と
  `sbx policy ls --json` の `rules`。詳細を開いたときと「更新」ボタンで取り直す。
  自動のポーリングやバッジ通知はしない
- **宛先ごとにまとめる**: `host`（`host:port`）が同じエントリは回数を合計し、
  最終時刻の新しい順に並べる
- **許可済みは出さない**: ログは履歴なので、許可した後も過去の拒否が残る。
  いまのルールと照合し、**当たる許可ルールがあり、当たる拒否ルールが無い**宛先は除く。
  照合は `sbx policy allow network --help` に書かれたパターン記法を自前で再現する
  （`*` は1ラベル内、`**.` は1つ以上のラベル、`?`、`[...]` / `[!...]`、`:port` の有無、
  IPv4 の CIDR）。効くルールは `status: active` かつ `resource_type: network` で、
  全体（`applies_to: all`）かこのサンドボックス（`applies_to: sandbox:<name>`）のもの。
  IPv6 の CIDR は判定しない（当たらない扱い＝一覧に残る。安全側に倒す）
- **許可の範囲は最小**: `sbx policy allow network --sandbox <このプロジェクト> <host:port>`。
  ログの `host:port` をそのまま渡す。全サンドボックスへの許可やワイルドカードは出さない
  （必要なら CLI で行う）
- **許可できるのは既定の拒否だけ**: `reason` に `default deny` を含むか、`rule` が
  `no applicable policies` で始まるものだけに「許可」ボタンを出す。それ以外（明示の拒否ルール、
  組織のポリシーなど）は許可ルールを足しても通らないので、理由の原文だけを出す。
  `reason` の値は公開ドキュメントに無く、2026-10-15 時点で実測できたのは
  `No matching allow rule (default deny)` のみ
- **確認する**: 許可は ① 隔離（architecture.md §6）を緩める操作なので、
  対象の宛先・範囲（このサンドボックスだけ）・データが外に出うること・ここからは取り消せないことを
  確認ダイアログで示す
- **無視リスト**: 毎回出るが許可したくない宛先（テレメトリなど）は「無視」にできる。
  `Project.ignoredNetworkHosts` にプロジェクト単位で保存し、一覧では折りたたんだ
  「無視した宛先」に移す。「無視をやめる」で戻せる
- **取り消しは作らない**: `sbx policy rm` を呼ぶ UI は持たない。必要になったら再検討する

**理由**

- サンドボックスの通信は既定で拒否されるため、エージェントの作業が通信エラーで失敗しても、
  利用者はその原因に気づけない。拒否の一覧を見せ、その場で許可できる導線が要る
- 許可は隔離を緩める操作なので、範囲は最小（このサンドボックス・この宛先とポート）に留め、
  広げる操作は CLI に任せる

## C-1 / C-2. セッション履歴：ローカル記録優先（Local Record First）

**決定（2026-09-29 改定）**

- セッションの**存在・一覧**はエージェント側に問い合わせる（`session/list`）。
  shovel が独自に「どんなセッションが存在するか」をでっち上げることはしない。
- しかし過去のやり取りの**内容**については、**ローカルスナップショットを正とする
  （Local Record First）**。ローカルスナップショットに1件でも記録があれば、
  `session/load` の replay によってそれを上書きしない。
- 要求書の「独自の履歴は持たない」は
  **「独自の履歴だけでセッションの存在を管理しない」**の意であり、この決定と
  矛盾しない。トランスクリプトの**内容**をローカルに保持し、それを優先すること
  自体は禁じられていない。

**理由**

エージェントは長い会話になるとコンテキストを要約・省略することがある。
`session/load` の replay は「エージェントが（要約後も）憶えていて語れる範囲」
でしかなく、実際にサンドボックス内のログとして残っている・かつてやり取りされた
内容の完全な記録ではない。一方でローカルスナップショットは、エージェントの
コンテキストウィンドウのサイズや要約方針に一切依存せず、やり取りされた情報を
そのまま保持できる。セッションで交わされた情報自体に価値がある以上、
**エージェント側のコンテキスト省略によって、ローカル側の表示がそれより劣化する
ことがあってはならない。** これが「エージェントを常に正とする」を採らない理由。

**これは 2026-09-16 時点の実装判断を覆す。** 当時は「replay を抑制すると
スナップショットとエージェントの記憶が食い違ったときに古い方を見せてしまう」
という懸念から、`load` のみのエージェントは常にライブ replay を正として上書き
していた。この懸念は「replay の方が新しい＝正しい」という前提に立っていたが、
その前提自体（要約により replay が情報として劣化しうる）が誤りだったと判断する。

**「保存」と「表示」は別の要件（2026-09-30 明確化）**

Local Record First は**保存**についての原則である：ローカルの記録は、
エージェントのコンテキストウィンドウのサイズや要約方針に合わせて切り詰めない。
消える・欠けるのはエージェント側の記憶であって、ローカルの記録ではない。

一方で**表示**（今まさにこのタブに描かれている内容）については、別の要件が働く：
**画面に表示されているものは、エージェントが実際に認識している内容と一致して
いることが望ましい**。ユーザーが送る次のプロンプトはエージェント側の（要約後の）
文脈の上に積まれるため、画面がエージェントの認識とズレたまま会話を続けると、
ユーザーから見えている文脈とエージェントが実際に参照する文脈が食い違う。

この2つは両立する：**保存されたローカル記録が失われることはない**（食い違いが
見つかった時点のものは必ずバックアップとして残る。C-4）が、**その時点で表示され
続けるかどうかは別の話**であり、エージェント側の記憶とズレたと分かった時点で
表示はエージェント側の最新の記憶に追従させる。「保存は切り詰めない／表示は
エージェントと一致させる」という2軸で理解する（詳細は C-4）。

**復元戦略（2026-09-30 改定：`load` を `resume` より優先する）**

| ローカルスナップショット | capability | 振る舞い |
| :--- | :--- | :--- |
| あり（1件以上） | `load` 対応（`resume` の可否は問わない） | スナップショットを即座に描画する。裏で `session/load` を送って文脈を再接続しつつ、返ってくる replay 通知は**画面には描画せず**別に記録しておき、ローカル記録と比較する（C-4）。一致すれば何もしない、食い違えば C-4 の手順でバックアップ＋表示更新 |
| あり（1件以上） | `load` 非対応・`resume` のみ対応 | スナップショットを描画し `session/resume` で文脈を再接続。`resume` は何も replay しないため**比較のしようがなく、無条件にローカルを信頼する** |
| 無し／空 | `load` か `resume` のいずれか対応 | `session/load` のライブ replay を描画し、完了後にそれを最初のスナップショットとして保存する |
| あり（1件以上） | 非対応 | **スナップショットのみ描画**（読み取り専用）。文脈の再接続はできない旨をユーザーに通知する |
| 無し／空 | 非対応 | 選択を拒否し、現在のセッションを維持する |

**優先順位が `resume` ではなく `load` である理由**: `resume` は文脈を再接続する
だけで何も replay しないため効率は良いが、ローカル記録とエージェントの記憶が
今も一致しているかを確認する手段が無い。`load` の replay だけがその確認手段に
なるため、両対応のエージェントでは `load` を選ぶ。

**スナップショットが必要な理由（Local Record First に加えて）**

1. **`session/list` も `session/load` も capability 依存。** 非対応エージェントでは
   履歴機能が丸ごと消える。
2. **ACP に `session/rename` が無い。** セッション名の上書きはクライアント側が
   持つしかない。
3. 上記の通り、**エージェント側の記憶がコンテキスト省略で欠落しうる**ため、
   ローカル記録そのものに独立した価値がある。

**実装上の要件**

- 保存先は**プロジェクトツリーの外**（VCS に載せない）。
- 書き込みは一時ファイル経由の**アトミックな move**（中断時の破損を防ぐ）。
- **`schemaVersion` を持つ。** 移行経路の無いバージョンは「履歴なし」として
  破棄する（読み込み失敗で接続そのものを壊さないため）。
- プロンプトを一度も受け取っていないセッションは、別セッションへ切り替える際に
  破棄する（空セッションがエージェント側に溜まるのを防ぐ）。

実装上の要所（この方針転換後も変わらない部分）:

- **エージェント側のセッション id をスナップショットに持つ**（`acpSessionId`）。
  `session/load` / `session/resume` が要求するのは shovel のタブ id ではなく
  こちら。これを持たない古いスナップショットは「非対応」と同じ扱いにする。
- **再開するタブの id には元のスナップショットの id をそのまま使う。**
  新しい UUID を振ると、同じ会話のスナップショットが2つに増える。

**実装済み（2026-09-30）**：`src/main/acp/connection.ts` の
`startRestoredSession` / `reconcileReplay` が上の復元戦略表どおりに動く
（ローカル記録があれば即座に描き、`load` の replay は描かずに C-4 の比較にだけ
使う）。なお「無し／空 × `resume` のみ対応」の行は、`session/load` が使えない
ため `session/resume` で再接続するだけになる（描けるものは無い）。

**この決定の帰結として重要度が上がった論点**：ローカル記録を正とするなら、
それを保護する仕組み（バックアップ・誤削除からの復旧・検索）が要る。
`open-issues.md` の C-4 / C-5 / C-6 を参照。

### C-1/C-2 補遺. 履歴一覧は `session/list` とローカル記録の和集合（2026-09-30 決定）

**決定**: チャット履歴パネルの「履歴」は、エージェントの `session/list` の結果と
ローカルスナップショットの**和集合**として作り、行ごとに「どちら側に存在するか」
の状態を表示する。

**経緯**: shovel の設計は「存在・一覧はエージェント側に
問い合わせる」としていたが、初期実装はローカル記録だけで一覧を作っており、
設計から外れていた。どちらか片方だけでは次のような欠落がある:

| | エージェント基準のみ | ローカル基準のみ（旧実装） |
| :--- | :--- | :--- |
| 同じサンドボックスでターミナルから動かしたセッション（C-3） | 出る | 出ない |
| エージェント側で消えたセッション | 出ない | 残り続ける（再開に失敗しうる） |
| 接続が無いとき・`list` 非対応のエージェント | 一覧が空 | 出る |
| ローカルにしか無い記録 | 検索でしか見つからない | 出る |

shovel は非エンジニアも使い、履歴はサイドバーに常設される（G-1-7）。接続前や
`list` 非対応のときに履歴が空になる、ローカル記録が検索でしか見つからない、
という状態は避けたい（Local Record First：記録そのものに価値がある）。一方で
C-3（ターミナルから動かしたセッションも見える）と「再開できるものが並ぶ」は
エージェント基準でないと実現できない。よって和集合を取り、違いは状態表示で
見せる。

**突合**: エージェント側の `sessionId` とスナップショットの `acpSessionId` で
対応を取る（`acpSessionId` を持たない古いスナップショットは「ローカルのみ」）。

**行の状態**:

| 状態 | 条件 | 表示・クリック時 |
| :--- | :--- | :--- |
| 両方にある | `session/list` にあり、ローカル記録もある | 通常表示。クリックでローカル記録を表示（`HistoryView`）→「再開」 |
| ローカルのみ | `session/list` を取得できたが、そこに無い | 「エージェントはこの会話を覚えていない」ことが分かる印。クリックでローカル記録を表示（再開は試みられるが失敗しうる） |
| エージェントのみ | `session/list` にあるが、ローカル記録が無い | 「ローカルに記録が無い」ことが分かる印。クリックで中身の無い `HistoryView`（説明＋「再開」）を開く。**クリックだけでは接続を張らない**（他の行と同じく、接続は「再開」を押したとき） |
| 不明 | `session/list` を取得できていない（接続が無い・`list` 非対応・失敗） | ローカル記録だけを通常表示し、「ローカルのみ」の印は付けない（確かめていないことを「無い」と表示しない） |

**一覧に出さないもの**:

- 今タブで開いているセッション（そのタブがいま接続している ACP セッション id）。
- ソフトデリート済み（C-5）: `.deleted` ファイルが持つ `acpSessionId` を
  目印として、`session/list` に残っていても一覧から除く。
- プロンプトを一度も受け取っていないセッション（エージェント側が返さない。
  下記「使われなかったセッションの破棄」）。

**取得**: `session/list` は、同じウィンドウで開いているライブタブの接続を1本
借りて呼ぶ（同じサンドボックス・同じエージェントなので、どのタブでもよい）。
`cwd` にはプロジェクトの `sandboxPath` を渡し、`nextCursor` を辿って全件を
取る。呼ぶ契機は、ウィンドウで最初の接続が確立したとき・各ターン
終了時・↻ とタブを閉じた後・削除の後。ライブタブが1つも無い間は「不明」の
扱いになる。

**タイトルの優先順位**: 名前の上書き（`sessionTitleStore`）＞ ローカル記録の
`title` ＞ エージェントの `title` ＞「名前のないセッション」。並び順は
ローカルの `savedAt` とエージェントの `updatedAt` の新しい方で降順。

**使われなかったセッションの破棄は実装しない**: プロンプトを一度も
受け取っていない ACP セッションを `session/delete` で消せば、開いてすぐ閉じた
タブが一覧に溜まるのを防げるが、**`claude-agent-acp` の `session/list` はプロンプト未送信のセッションを
そもそも返さない（2026-09-30 実機確認）**ため、防ぐ対象が無い。一覧に出ない
セッションがエージェント側に残っても利用者からは見えないので、作らない
（「作らずに済むものは作らない」）。未送信のセッションを一覧に返すエージェントを
追加したときに、その時点で入れる。ローカルは元々空の記録を残さない。

**ローカル検索（C-6）は対象を変えない**: 検索はローカル記録の平文に対して行う
ため、「エージェントのみ」の行は検索に出ない。

**実装済み（2026-09-30）**: `sessionManager.ts` の `listHistory()`（和集合と
除外）・`deleteHistorySession()`（`session/delete` ＋ソフトデリート）・
`resumeAgentSession()`（「エージェントのみ」の行の再開。書き込み先の
スナップショット id とタブ id は新しく振る）。状態アイコンは「エージェントのみ」
が雲、「ローカルのみ」が斜線入りの雲。

### C-3. 「アプリ外のセッション」の範囲

**決定**: **同一サンドボックス内でターミナルから動かしたセッション**を指す。

- `session/list` はサンドボックス内のエージェントに問い合わせるため、
  同じサンドボックスでターミナルから動かしたセッションは列挙される。
- **範囲外**: 別サンドボックスのセッション、別エージェントのセッション、
  ホスト側で直接動かしたセッション。いずれも ACP 経由では原理的に取得できない。

### C-4. バックアップ（食い違いを検出したときの保険）

**採用（2026-09-30）。**

C-1/C-2 で「表示はエージェント側の最新の記憶に追従させる」と決めた以上、
追従の瞬間にそれまでのローカル記録を消してしまわないための保険が要る。
これが C-4 の役割：**バックアップは保存を切り詰めないためのものであり、
表示をエージェントに追従させること自体は妨げない。**

**発生条件**: ローカルにスナップショットがあり、かつエージェントが `load` に
対応しているときだけ発生する（C-1/C-2 の復元戦略表）。`resume` のみのエージェント
では replay が起きないので比較しようがなく、バックアップも発生しない。

**比較ロジック（ACP `agent_message_chunk` の `messageId` のみで比較する）**

- 比較するのは **`agent_message` エントリの `messageId`** だけ。出現順に並べ、
  同じ id が連続する場合は1回に畳む（tool call や thought を挟んでも同じ
  メッセージの分割とみなす）。
- **プロンプトは比較しない**（IDE 側から送るプロンプトには id が無い）。
- **tool call も比較しない**（最終状態や content が違っても差分扱いにしない）。
- テキスト内容そのものは比較しない。`messageId` は同じ発言が live でも replay
  でも同じ id を持つ、という ACP の性質だけに依拠する（`messageId` は ACP v1
  `agent_message_chunk` の**任意**フィールド。後述の検証事項を参照）。
- どちらか一方にでも `messageId` の無いエントリがあれば「差分あり」。ただし
  **replay 側が1件も `messageId` を持たない場合は「比較不能」として扱い、
  何もしない（ローカルをそのまま維持）**。エージェントが `messageId` を一切
  送らない場合、この仕組みは常に「ローカル据え置き」に倒れる。

**食い違いが見つかったときの挙動**:

1. 一致 → 何もしない。ローカルスナップショットがそのまま表示され続ける。
2. 不一致 → 現在のローカルスナップショットを `{sessionId}.json.{epochMillis}.backup`
   として**まず退避してから**、replay された内容を新しい `{sessionId}.json`
   として書き込み、**画面もその内容に描画し直す**。つまり**食い違った時点で
   表示上の正はエージェント側の最新の記憶に切り替わり**、それまでのローカル
   記録はバックアップとしてのみ残る（既定表示ではなくなる）。

**比較の記録（2026-10-01 追記）**: 比較のたびに、セッションログ
（`userData/logs/{projectId}/…log`、プロジェクト詳細の「ログ」から開ける）へ
`{ms} DEBUG replay-compare snapshot=… verdict=… {…}` の1行を書く。中身は比べた
`messageId` の並び（`localIds` / `replayIds`）、最初に食い違った位置
（`firstMismatch`）、片側にしか無い id（`onlyInLocal` / `onlyInReplay`）、
`messageId` を持たない AGENT エントリの先頭部分（`localWithoutId` / `replayWithoutId`）。
「毎回差分ありになる」ような事象の原因を、実機のログから特定するためのもの。

**保存先はプロジェクトごと（2026-10-01 変更）**: ローカル記録は
`userData/snapshots/{projectId}/`、ログは `userData/logs/{projectId}/{ms}_{sessionId}.log` に
置く（以前は全プロジェクト共通の1ディレクトリ）。一覧・ローカル検索が他の
プロジェクトの記録を読まずに済み、プロジェクト詳細の「開く」もそのプロジェクトの
分だけを見せられる。旧形式のファイルは起動時に移す（`migrateFlatSnapshots` /
`migrateFlatLogs`。移し先に同名があれば移さず残す）。プロジェクトの削除では
そのプロジェクトのローカル記録ディレクトリを丸ごと消す。

**replay の取りこぼし（2026-10-01 修正）**: 「毎回差分あり」の原因は shovel 側の
競合だった。ACP SDK は `session/load` の応答を受け取った瞬間に request を解決するが、
通知（`session/update`）はいくつかのハンドラを await で経由してから届く。そのため
応答の直前に届いた replay の末尾（たいていエージェントの最後の発言）が、await が
返った時点ではまだ届いておらず、「ここまでが過去分」の確定から漏れていた
（漏れるかどうかがタイミング次第のため、再開のたびに結果が揺れた）。受信した
`session/update` をストリーム層（SDK に渡す前）で数え、ManualSession が同じ通数を
受け取るまで待ってから replay を確定するようにした。セッションログには
`DEBUG replay-delivery … expected=… receivedAtResponse=… received=…` を残す。

**比較しないものも保存はする（2026-10-01 追記）**: スナップショットには比較対象の
AGENT エントリだけでなく、tool call のグループ（`role: 'TOOL_GROUP'`、各ツールコールの
種類・タイトル・状態・場所・diff・中身。`rawInput` は表示に使わず diff と重複するため
除く）、USER の添付チップ、AGENT の選択肢も保存する。並び順は画面と同じ
（ブロックとグループは最初に現れた位置、思考は確定した位置）。

**「保存」と「表示」の分離を実現する部分がここ**：切り詰められるのは表示だけで、
バックアップに退避したローカル記録の**内容は消えない**（C-1/C-2 の理由参照）。

**競合防止**: この比較・置き換えは接続の裏側で非同期に行われるため、比較が
終わるまでの間にユーザーが別セッションへ移動した、または新しいターンを実行した
場合は、結果を握りつぶして何もしない。

**バックアップは自動削除しない**: **バックアップファイルは無期限に残す。** セッション一覧
などの UI 表示は新しい方から一定件数に絞ってよいが、それは表示上の
話であり、ファイル自体は消さない（古いものは C-6 のローカル検索でのみ発掘する）。

**`messageId` を送るかは検証済み（V-19、2026-09-30）**: shovel が主対象とする
`@agentclientprotocol/claude-agent-acp` は `agent_message_chunk` に `messageId`
を実際に付けて送ってくることを確認した。この比較ロジックは主対象のエージェント
で機能する前提で進めてよい。

**UI（2026-09-30 決定。詳細は `ui.md`「チャット履歴パネル」）**:

- バックアップの保存先は C-1/C-2 と同じ場所（プロジェクト外、VCS 対象外）。
- サイドバーのチャット履歴パネルで、バックアップを持つセッション行に展開
  キャレットを付け、開くと新しい順に `{日時} {サイズ}` のサブリストが現れる
  （表示は新しい20件まで、ファイル自体は無期限に残す）。行クリックで
  Read Only タブ（既存の `HistoryView` を `readOnlyKind: 'backup'` 付きで
  流用。「再開」「新規開始」は出さない）として開く。
- **食い違いが検出され、表示中のタブの内容が置き換わったときは、トランスク
  リプトに控えめな notice 行を1行差し込み、利用者が気付けるようにする**
  （C-1/C-2 の出発点が「情報が失われることがある」への懸念だったため、それが
  実際に起きたことを利用者が発見できる経路を残したい）。

**実装済み（2026-09-30）**: `SnapshotEntry.messageId`（AGENT エントリのみ）、
`snapshot.ts` の `backupSnapshot()`（タイムスタンプ衝突時は +1ms でリトライ、
一時ファイル経由の atomic move）、`connection.ts` の `compareByMessageId()` /
`reconcileReplay()`（競合防止は `restoreEpoch` という世代番号で行う。新しい
ターン・↻・タブを閉じる操作で進み、比較の途中で進んでいたら結果を捨てる）。

### C-5. ソフトデリート ＋ Read Only タブ

**方向性を採用（2026-09-29）。`flows.md` の「削除は常にローカルのスナップショットと
メタデータを破棄する」という現行記述は撤回する。**

Local Record First を採る以上、セッション削除も「誤操作からの復旧が効かない
即時完全削除」のままでは一貫しない。次の方向で進める：

- `session/delete`（対応していれば。失敗しても続行）を送った上で、
  ローカルスナップショットは即座に消さず `{sessionId}.json.{epochMillis}.deleted`
  （削除した時刻）へリネームして退避する。削除されたセッションはセッション
  一覧には出さない。
- **そのセッションが C-4 で作られたバックアップを持っていれば、それらも
  1つずつ `{sessionId}.json.{backupの元のepochMillis}.deleted` へリネームする
  （バックアップが取られた時刻を保ったまま）。** バックアップを `.backup` の
  ままにして本体だけ消すと、削除したはずのセッションがローカル検索(C-6)の
  通常検索（削除済みを含めない設定）に引っかかり続けてしまうため。
- 本体のリネームを先に行い、それが失敗したらバックアップには触らない
  （どの段階で失敗しても、セッションが「一覧には出ないのに一部のファイルだけ
  検索に残る」半端な状態にならないようにする）。
- 退避された記録は、閲覧専用の **Read Only タブ**（サンドボックスに接続しない、
  プロンプト入力欄やコンテキストチップを持たない）で再度開ける。
- Read Only タブは通常タブと同じ最大10タブの上限に含める。

**UI（2026-09-30 決定。詳細は `ui.md`「チャット履歴パネル」）**:

- セッション一覧はサイドバー常設なので、**サイドバー自体に「削除済みを表示」トグル**（既定
  OFF）を置く。ON にすると履歴リストの下にグレーアウトした削除済みセクション
  が現れ、行クリックで Read Only タブ（`readOnlyKind: 'deleted'`）として開く。
  これなら C-6（ローカル全文検索）が無くても最低限の復旧導線が成立するため、
  C-6 より先に実装できる。
- Read Only タブは既存の `HistoryView` を流用し、`readOnlyKind` に応じて上部
  バーの文言を `Backup · {日時}` / `Deleted · {日時}` に切り替え、「再開」
  「新規開始」ボタンは両方隠す。バックアップ／削除済みの内容を今のライブ
  セッションへ書き戻す操作は提供しない。
- バックアップ／削除済みタブの識別子は本セッションの `sessionId` と衝突する
  ため `{sessionId}::backup::{epochMillis}` のような合成 id を使う。同じ
  ファイルを複数タブで開くことも禁止しない（重複オープンのロックは無し）。

**`session/delete` の送り方（2026-09-30 追記。C-1/C-2 補遺の和集合一覧に伴う）**:
履歴一覧に `session/list` の結果が入るため、ローカルだけ削除するとそのセッションは
「エージェントのみ」の行として一覧に戻ってくる。そこで次のようにする:

- 同じウィンドウにライブタブがあり、エージェントが `delete` に対応していれば、
  その接続を借りて `session/delete` を送る（失敗しても続行）。
- 送れないとき（ライブタブが無い・`delete` 非対応・失敗）でも、`.deleted`
  ファイルが持つ `acpSessionId` を目印に一覧から除外するため、一覧上の結果は
  同じになる。**ライブタブを開いてから削除するよう促すことはしない**。確認
  ダイアログは「このアプリの一覧から削除されます。記録は『削除済みを表示』から
  読み取り専用で開けます」程度の中立な文言にし、エージェント側が残るかどうかを
  利用者の判断材料として求めない。
- 「エージェントのみ」の行（ローカル記録が無い）は、退避すべきファイルが無い。
  `session/delete` を送れるときだけ削除でき、送れないときは削除メニューを
  無効にする（目印にするためだけの空の記録は作らない）。名前変更も、ローカル
  記録ができる（一度「再開」する）までは無効にする。

**退避したファイルを完全に消すタイミングは設けない**: C-4 のバックアップと
同じく無期限に残す。ディスク容量は増え続けるが、消してしまうと「誤って
削除したセッションを取り戻す」という C-5 の目的そのものが壊れるため、
自動的な完全削除は行わない（必要になれば利用者が手動でファイルを消せる場所に
保存する、という以上のことはしない）。

**実装済み（2026-09-30）**: `snapshot.ts` の `softDeleteSnapshot()`（本体→
バックアップの順にリネーム。本体のリネームが失敗したら例外を投げ、バック
アップには触らない）。なお `session/delete` の送信は未実装（過去セッションには
接続が無く、送るには削除のためだけに接続を張る必要があるため）。

### C-6. ローカルセッション検索

**入り口の配置・検索範囲・表示条件・結果表示（ポップアップの中身）を決定
（2026-09-30）。**

C-4/C-5 でバックアップ・削除済みセッションを退避するようになると、それらを
見つけ出す手段が要る。

**入り口の配置（`ui.md`「チャット履歴パネル」参照）**: セッション一覧がサイドバー
常設（G-1-2）なので、**チャット履歴パネルの「履歴」見出しの右寄せに検索
アイコン（🔎）を置く**。タブバーやツールバーには置かない：shovel のタブは
`session` / `file`（Markdown）/ `history` が混在するため、そこに検索を置くと
「今開いているファイルの検索か、トランスクリプト内検索（V-5、`findInPage`）か、
セッション横断検索か」が曖昧になる。履歴パネルの見出しに紐づけることで、
位置だけでセッション検索だと伝わる。

**検索範囲は「履歴」に限定しない**: アイコンの置き場所は「履歴」見出しだが、
検索対象は**プロジェクトの全ローカルスナップショットファイル**（今開いている
タブの `.json` を含む、`.backup` / `.deleted` も含む）。置き場所と範囲は別の
話——今開いているタブの本体はトランスクリプト内検索で足りるが、そのタブに
紐づく `.backup` は現在のタブ表示の下には出てこないため、検索対象から外すと
発見できなくなる。

**表示条件**: 「履歴」見出し自体を `pastHistory.length > 0` のときだけ出す
現状のままだと、「過去セッションは無いが、今開いているセッションのバック
アップだけ存在する」場合に検索の入り口ごと消えてしまう。見出し・アイコンの
表示条件は「プロジェクトに何らかのローカルスナップショット（現在・バック
アップ・削除済みいずれか）が1件でもあるか」に揃える。

**結果の見せ方**：shovel はエンジニア限定のアプリではないため、**Gemini のセッション
検索のような平易な結果表示**を採用する。

```
┌──────────────────────────────────────────┐
│ 🔎  [検索キーワード入力]              ✕  │
└──────────────────────────────────────────┘
□ 削除済みも含める

結果
社内ツール改修の相談
このバグは sbx exec の stdout/stderr 分離が原因で...        9月15日
テスト設計の下書き                              バックアップ・9月10日
sbx の path 解決を直したのはこのセッションで...
```

- **結果行**：タイトル（太字）＋マッチ箇所を含む一文を**プレーンテキストで
  抜粋**（`SnapshotEntry.markdown` から Markdown 記法を落とした平文から作る。
  マッチ語だけ太字）＋右寄せの日付（月日、年内は年を省略）。**プレビュー欄は
  無い**：結果行自体がスニペットを兼ねる。
- **バックアップ／削除済みの行だけ**、右側の日付表示を「バックアップ・{日付}」
  「削除済み・{日付}」に置き換える（通常セッションの行は日付のみ）。アイコン
  は使わず、Gemini 同様テキストだけで区別する。
- **マッチングは生 JSON の文字列ではなく、抽出した平文に対して行う**。デバウンス約200ms・
  メインプロセス側の非同期処理で実行・新しいクエリが来たら前の検索をキャンセルする。
- 「削除済みも含める」チェックボックスは検索欄の直下に置く。
- 結果を開いたときの遷移は変更なし：`.json`（現行セッション）はアクティブな
  タブで開き直し、`.backup` / `.deleted` は Read Only タブで開く。
