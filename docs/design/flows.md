# 主要フロー

「なぜそう決めたか」は [decisions.md](./decisions.md) を参照。

---

## 1. 初回起動

```
1. 前提チェック    sbx diagnose を実行
                  ├─ 成功 → 次へ
                  └─ 失敗 → 出力をそのまま見せ、対処を案内する
                            （「環境が悪い」ではなく「こうすれば直る」を示す）
                            sbx login が要るなら ［ターミナルを開いてログイン］

2. プロジェクトマネージャを開く
                  空状態では「最初のプロジェクトを作る」を大きく出す
```

**エージェントの認証は初回起動時に聞かない。** 状態はいつでも
`claude auth status --json` で分かるため、**必要になった時点で必要な人にだけ**
出す（§2-4 の作成フロー、または §3 の接続前）。すでにログイン済みの人には
何も聞かない。

## 1-2. 認証（必要と分かったときだけ）

認証は**サンドボックス間で共有される**ため、一度ログインすれば全プロジェクトで
効く。**プロジェクト作成フローにログインステップは入れない。**

```
sbx exec <name> claude auth status --json     ← 高速な事前チェック
  │                                              真実は接続時の認証エラー（下記）
  ├─ loggedIn: true  → 何もしない。そのまま接続へ
  │
  └─ loggedIn: false → 認証画面
       ├─ ［ターミナルを開いてログイン］     ← 既定・推奨
       │     OS のターミナルで
       │     sbx exec -it <name> claude auth login
       │     ブラウザでの認証はターミナルとエージェントに任せる
       │     （--claudeai が既定。--console / --sso も選べる）
       │
       └─ ［API キーを使う］
             値を sbx secret set anthropic の stdin へ渡す
             （-t/--token は使わない。help に
               "less secure: visible in shell history" と明記）
  │
  └─ ［確認］→ 再度 status を取得 → loggedIn: true なら接続へ
```

**shovel は OAuth を一切実装しない。** ブラウザの起動も、コールバックの受け取りも、
コードの貼り付けも、すべてターミナルとエージェントの責任。
これは「ターミナルは組み込まず、OS のターミナルを借りる」（§9）と同じ判断。

`sbx login`（Docker へのサインイン）も同じ扱い。`sbx diagnose` で検出し、
ターミナルへ誘導する。

### `loggedIn` 以外のフィールドに依存しない

一度もログインしていない新しいサンドボックスでも `loggedIn: true` が返るが、
そのとき `email` / `orgId` / `subscriptionType` は `null` で、
`configDirectory` / `projectsDirectory` に至っては**キーごと欠落する**
（初回の対話まで埋まらない）。

- **`loggedIn` だけで分岐する**
- 他のフィールドは**無い前提**で扱い、あれば表示に使う程度に留める
- 「Pro で利用中」のような `subscriptionType` 依存の表示は作らない

### 接続時の認証エラーも同じ画面へ導く

`loggedIn: true` は「使えるはず」という申告であって、API が通る保証ではない
（トークンの期限切れで嘘になりうる）。**接続やターンが認証エラーで失敗したら、
同じ認証画面を出す。**

`auth status` だけに頼ると期限切れのときに原因不明の接続失敗になり、
接続エラーだけに頼ると未認証の人が毎回失敗を見てから案内される。**両方持つ。**

## 2. プロジェクト作成

### フロー1：新規ディレクトリ作成（推奨・既定）

```
1. エージェントを選ぶ              ← 対応表の verified のみ
2. プロジェクト名を入力             ← displayName。日本語可
3. ベースディレクトリを選択
4. プロジェクトパスを確認           ← 編集可
   ─── 詳細（折りたたみ）─────────────────
   サンドボックス名                 ← 自動導出。編集可
5. 作成 → §2-4 の共通処理へ
```

### フロー2：既存ディレクトリ追加

```
1. プロジェクトパスを選択
2. エージェントを選ぶ
3. プロジェクト名を確認             ← 既定はディレクトリ名
4. 警告と同意
   「このディレクトリ内のファイルは、隠しファイルを含めすべて AI に参照されます」
5. 作成 → §2-4 の共通処理へ
```

### フロー3：既存サンドボックスから追加

`sbx ls --json` にあって shovel の一覧に無いものを提示する。
エージェントもパスも `sbx` が知っているため、聞くのは表示名だけ。

```
1. 一覧から選ぶ    ← name / agent / workspaces / status が取れる
2. 表示名を確認    ← 既定はサンドボックス名
3. 追加           ← sbx create は行わない。sandboxPath の実測のみ行う
```

### 2-4. 共通処理（作成フローの中で完了まで待つ）

```
1. ディレクトリを用意             （フロー1 のみ）
2. sbx create <sbxAgent> <hostPath> --name <sandboxName>
     ↑ 初回はイメージ取得で数分かかりうる。進捗を必ず表示する
3. sbx exec <sandboxName> pwd    → sandboxPath を実測して保存
4. 認証情報の確認・設定           （未設定なら）
5. Project を永続化
6. ウィンドウを開く
```

**登録だけ先に済ませる方式は採らない。** 「登録は成功したのに、後で開いたら
動かない」は、非エンジニアには原因の分からない体験になる。作成フローの中なら
「今何をしているか」を説明しながら待たせられる。

## 3. ウィンドウを開く 〜 ACP 接続

```
[プロジェクトを開く]
  │
  ├─ すでにウィンドウがあれば、そのウィンドウを前面に出して終了
  │   （プロジェクトは常に新しいウィンドウで開く。「現在のウィンドウで開く」は無い）
  │
  ├─ BrowserWindow を生成
  │
  ├─ 前回開いていたタブを左から並べる（decisions.md G-1-17）
  │   セッションのタブは接続せず履歴のタブとして開く。消えたファイル・記録のタブは外す
  │
  ├─ ACP アダプタの更新確認（decisions.md N-2-5b）
  │   記録した acpVersion より、プロジェクトマネージャを開いたときに ACP レジストリで
  │   控えた最新版が新しければ「更新する／今のバージョンのまま」を尋ねる。答えてから次へ
  │
  └─ 新しいチャットを一番右に開いて接続を開始（「+」で2つ目以降を開くときも同じ）
       │   接続中タブを即座に出し、以下の段階を進むたびに表示を更新する（下記「接続中タブ」）
       │
       ├─ 0. 認証状態の確認  sbx exec <name> claude auth status --json（1-2 節）
       │
       ├─ 1. 生存確認     sbx exec -i <name> echo ...    終了コードのみで判定
       │                   失敗 → エラー表示。接続を試みない
       │
       ├─ 2. プロセス起動  sbx exec -i <name> npx -y <acpPackage>@<version>
       │                   version = acpVersion → 控えた最新版 → latest の順
       │                   stdout → ACP パーサ / stderr → ログと進捗表示へ分離
       │
       ├─ 3. initialize   protocolVersion: 1, clientInfo
       │                   応答の agentInfo.version を Project.acpVersion に記録
       │                   fs.readTextFile / fs.writeTextFile / terminal = false
       │                   ← アイドルタイムアウト（既定180秒。無音時間で測る）
       │
       ├─ 4. session/list  （sessionCapabilities.list があれば）
       │
       └─ 5. session/new   cwd = sandboxPath, mcpServers = []
                           ← sessionId / models / modes / configOptions
```

### 接続中タブ

「+」を押してから接続が終わるまでには、`sbx exec` 2回（認証確認・生存確認）と
`npx` によるアダプタの起動を直列に待つため、数秒〜数十秒かかる。接続を待ってからタブを出すと
押しても何も起きないように見えるので、**タブは押した直後に出し、いま何を実行しているかを正直に見せる**。

- 段階は「ログイン状態の確認 → サンドボックスへの到達確認 → エージェント（ACP アダプタ）の起動 →
  セッションの開始」の4つ（`SessionOpenStep`）。各段階で実行しているコマンド／メソッド
  （`sbx exec <name> echo`、`npx -y <package>@<version>`、`session/new` など）と経過秒数を出す
- ログイン状態の確認は renderer が `auth.status` を呼ぶ前に自分で積み、残りは main が
  `session:openProgress` で知らせる（`openTab` に渡した `requestId` で接続中タブと対応づける）
- エージェントの起動は `npx` のパッケージ取得と `initialize` の応答待ちを区別できないので1つの段階にまとめ、
  「初回やバージョン更新時は時間がかかる」と添える
- 接続できたら、その接続中タブをその場でセッションタブに差し替える（タブの位置・名前はそのまま）
- 失敗したら、止まった段階とエラーをそのタブに出し、再試行・閉じるを選ばせる。
  未ログイン（認証確認・接続時の認証エラー）のときはタブを閉じて認証画面を出す
- 接続中に閉じたタブは、接続が終わったところで main 側のセッションも閉じる

`sbx exec` は停止中のサンドボックスを自動的に起動するため、**「起動」という
操作は存在しない**。

## 4. ターンの実行

```
[ユーザーがプロンプトを送信]
  │
  ├─ 0. 未保存の編集をディスクへフラッシュ（autosave のデバウンスを飛ばす）
  │      エージェントは IDE のバッファではなくディスクを読むため。
  │      書き込みの完了を待ってから 1. に進む
  │      （添付は resource_link でパスだけを送るので。decisions.md G-1-5a）
  │
  ├─ 0. トランスクリプトを最下部へスクロール
  │
  ├─ 1. session/prompt を送信（タイムアウトなし）
  │      Send ボタンが Stop に変わる
  │
  ├─ 2. session/update を受信し続ける
  │      agent_message_chunk  → ストリーミング表示（プレーンテキスト）
  │      agent_thought_chunk  → 入力欄の上の専用エリアに直近数行
  │      tool_call            → ツールカード。グループに畳む
  │      tool_call_update     → 同じカードを更新
  │      plan                 → タスクリストカード
  │      usage_update         → トークン使用量
  │      （ブロック確定時に Markdown で描画し直す）
  │
  ├─ 3. session/request_permission が来たら → §5
  │
  └─ 4. ターン終了（stopReason）
         ├─ 思考ログを折り畳んでログ下部へ格納
         ├─ ツールコールグループを閉じる（Working… 12s → Worked 12s）
         ├─ 展開中フォルダを readdir し直す
         ├─ 開いているファイルを読み直す
         └─ スナップショットを保存
```

### 中断

Stop ボタンで `session/cancel`（通知）を送る。`session/prompt` は
`stopReason` を伴って応答する。

### ターン終了は通知しない

背景タブにターン終了のバッジは出さない。**どのタブもターンを終えるため、
通知するとタブ列全体が光り続ける。**

## 5. 権限要求

```
エージェント → session/request_permission
  │
  ├─ 前面のタブ    → インライン承認カードを表示
  └─ 背景のタブ    → タブのアイコンにバッジ（前面のタブには出さない）
       │
       ├─ ボタンは options から生成する
       │   （allow_once / allow_always / reject_once / reject_always）
       │   クライアント側で選択肢を発明しない
       │
       ├─ ファイル変更の場合: ファイル名と行数の増減（+15 -3）を1行で表示
       │                      チャット内に diff は展開しない。クリックで Diff ビューへ
       ├─ コマンド実行の場合: rawInput から実行されるコマンドを抽出して表示
       └─ switch_mode の場合: 選択肢は許可/拒否ではなく遷移先のモード。
                             枠付きブロックで plan を Markdown 展開する
  │
  └─ 選択 → outcome を返す。ボタンを無効化し、選んだ結果をカードに残す
            ターンがキャンセルされた場合は cancelled を返す
```

**shovel は独自の自動承認を実装しない。** 「どこまで自動で許すか」は
エージェントの Mode（`session/set_mode`）の責任とする。繰り返しの確認を
避けたい利用者は、エージェントが提供する `allow_always` を選ぶ。

## 6. セッションの復元

```
[セッション履歴サイドバーの行をクリック / 別タブアイコンをクリック]
  │
  ├─ クリック          → 現在のタブで開く
  ├─ 右端のアイコン    → 別タブで開く（新しい接続を確立）
  └─ 右クリック        → 別タブで開く / 名前変更 / 削除
  │
  └─ ローカルスナップショットの有無 × エージェントの capability で分岐
     （Local Record First。鮮度＝保存時刻の新旧は比較しない。decisions.md C-1/C-2）
       │
       ├─ あり(1件以上) × load 対応     → スナップショット描画 + session/load
       │                                   （replay 通知は描画せず messageId で比較。
       │                                     食い違えば .backup へ退避して表示を置換。
       │                                     decisions.md C-4）
       ├─ あり(1件以上) × resume のみ   → スナップショット描画 + session/resume
       ├─ 無し/空       × load か resume → session/load のライブ replay を描画
       │                                   完了後に新しいスナップショットを保存
       ├─ あり(1件以上) × 非対応        → スナップショットのみ描画
       │                                   「文脈の再接続はできません」と通知
       └─ 無し/空       × 非対応        → 選択を拒否し、現在のセッションを維持
```

ローカルスナップショットが1件でもあれば、それを `session/load` の replay で
上書きしない。エージェントは長い会話でコンテキストを要約・省略することがあり、
replay は「エージェントが憶えていて語れる範囲」でしかないため。

### セッションの開始方法は2種類

| 操作 | 接続 | 意味 |
| :--- | :--- | :--- |
| **タブ列の `+`** | **新しい接続を確立** | 別件を並行して始める |
| **タブ上部のリフレッシュマーク** | **今の接続を再利用**して `session/new` | このタブをリフレッシュする |

接続の確立は高価（プロセス起動と `npx` によるアダプタ取得）なので、
**可能な限り接続を再利用する**ための軽い経路を別に用意する。

### 名前変更と削除

- **名前変更**: ACP に `session/rename` が無いため、shovel 側にタイトルの
  上書きを保存し、エージェントが報告するタイトルより優先する
- **削除**: `session/delete`（対応していれば。失敗しても続行）を送る。
  **ローカルのスナップショットは即座に破棄しない**（Local Record First、
  decisions.md C-1/C-2）。`{sessionId}.json.{epochMillis}.deleted` へ
  リネームして退避し、**そのセッションのバックアップ(C-4)があれば1つずつ
  同様に `.deleted` へリネームする**（バックアップを消してしまうと、削除済み
  セッションが通常のローカル検索に残り続けてしまうため）。一覧には出さないが
  Read Only タブから再度開ける（decisions.md C-5）

## 7. 編集の競合

Markdown エディタは **autosave**（入力が止まって数百ms〜1秒。連続入力に備えて
最大待ち時間も設ける）。UI に「保存」ボタンを出さない。

```
[開いているファイルが外部で変わった]
  │
  ├─ 未保存の編集が無い  → 黙って再読込
  │
  └─ 未保存の編集がある
       ├─ 1. ユーザーの版を別名で保存
       │      spec.conflict-20260914-153012.md
       │      （<名前>.conflict-<YYYYMMDD-HHmmss>.<拡張子>）
       ├─ 2. エディタを最新（AI の版）に更新
       └─ 3. 通知バー
              「AI がこのファイルを変更したため、あなたの編集を
                spec.conflict-20260914-153012.md に保存しました ［開く］」
```

**ロック・3択の競合ダイアログ・Diff 表示はいずれも作らない。**
ファイルが削除されていた場合は「このファイルは削除されました」と明示するに
留める（decisions.md A-3-8 で shovel 側の復元機能を廃止したため、案内は
出さない。git 管理下のプロジェクトなら、復元は使い手が普段使っている git で
行える）。

## 8. コマンド実行

```
[サイドバー下付きの「コマンド実行」を開く]
  │
  ├─ コマンドを入力（履歴はプロジェクト単位）
  │
  ├─ sbx exec -i -w <sandboxPath> <sandboxName> <command>
  │    ※ -t は付けない（TTY なし）
  │
  ├─ 出力をストリーム表示
  │    ANSI エスケープは除去。\r で上書きされる進捗行は1行として畳む
  │    出力行数に上限を設け、超えた分は古い行から捨てる
  │
  ├─ 実行中は入力欄から stdin へ文字を送れる（[Y/n] などに答えられる）
  │
  └─ 中断ボタンは常に押せる
```

### TTY モード

カーソルで選ぶ・スペースで選ぶような TUI は、上の流れでは動かない。
実行前に TTY モードに切り替えると、次の流れになる（decisions.md N-4「TTY モード」）。

```
[TTY モードをオンにしてコマンドを実行]
  │
  ├─ xterm.js の面をドロワーに出し、その列数・行数を測る
  │
  ├─ sbx exec -i -w <sandboxPath> <sandboxName> /bin/sh -c '<python3 の確認と exec>' \
  │      <ラッパー（base64）> <列> <行> /bin/sh -lc <command>
  │    ├─ python3 が無い → stderr の目印で判別 →「このサンドボックスでは TTY モードを使えません」
  │    └─ ラッパーが PTY を作り、TERM=xterm-256color でコマンドを動かす
  │
  ├─ 出力のバイト列をそのまま xterm.js に流す（ANSI は除去しない）
  ├─ キー入力は xterm.js が作ったバイト列をそのまま stdin へ（Ctrl+C も \x03 のまま）
  ├─ 面の大きさが変わったら、stdin に ESC ] 777;shovel-resize;<列>;<行> BEL を送る
  │
  ├─ 中断ボタン（実行中にドロワーを閉じた場合も）: stdin を閉じる → ラッパーが子に SIGHUP。終わらなければ kill
  │
  └─ 終了: 終了コードを表示。面は次の実行かドロワーを閉じるまで残す（保存はしない）
```

`vim` などの全画面アプリも TTY モードで動く。サンドボックスに `python3` が無い場合は、
**「プロジェクトの詳細」から OS のターミナルアプリを開く**
（`sbx exec -it <sandbox> /bin/bash -l` を渡す）。

コマンド実行は承認カードを通らない（ユーザー自身が打つものだから）。
守りは①隔離（サンドボックス外は無事）が担う（architecture.md §6）。

## 9. プロジェクトの削除

```
[プロジェクトマネージャ → 削除]
  │
  ├─ 確認ダイアログ
  │    ☐ ローカルのディレクトリも削除する    ← 既定 OFF
  │
  ├─ sbx rm --force <sandboxName>
  │    （shovel は非対話なので --force。確認 UI は shovel 側で出す）
  │    ※ sbx rm はホストのワークスペースを削除しない
  │
  ├─ チェックが ON の場合のみ:
  │    shell.trashItem(hostPath)   ← fs.rm ではなく OS のゴミ箱へ
  │
  └─ Project とスナップショット、開いていたタブの控えを破棄
```

## 10. 状態の突き合わせ（起動時）

```
[アプリ起動 / プロジェクトマネージャを開く]
  │
  ├─ sbx ls --json が失敗した、または shovel にあって sbx に無いものがある
  │    └─ sbx diagnose --json で原因を確かめる（ls が全件そろっていれば走らせない）
  │         ├─ sbx が無い                    → 案内を出し、全件「状態不明」
  │         ├─ Authentication が fail        → 「Docker にサインインしていません」＋［サインイン…］
  │         │                                   （OS のターミナルで sbx login）＋［再確認］、全件「状態不明」
  │         └─ ls が失敗し、原因が分からない → 「一覧を取得できませんでした」＋［再確認］、全件「状態不明」
  │    未サインインだと sbx ls は失敗する（または空を返す）。それを「サンドボックスがありません」と
  │    誤表示しないため。案内が出ている間は、ウィンドウにフォーカスが戻るたびに確かめ直す。
  └─ sbx ls --json と shovel の設定を突き合わせる
       ├─ shovel にあって sbx に無い  → 「サンドボックスがありません」＋［再作成］
       │                                 設定は消さない
       ├─ sbx にあって shovel に無い  → 「既存のサンドボックスから追加」に出す
       ├─ workspace_missing: true     → ホストのディレクトリが消えている旨を提示
       └─ status: "stopped"           → 何もしない（開けば自動起動する）
```

**自動で消さない・自動で足さない。** 見せて選ばせる。
