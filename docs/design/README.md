# shovel 設計ドキュメント

**shovel（シャベル）** は、Docker Sandboxes の中で動く AI エージェントを、
ACP（Agent Client Protocol）でホスト PC から操作する**チャットアプリケーション**である。

---

## このアプリが解こうとしていること

AI エージェントに開発を任せるとき、2つの問題がある。

1. **エージェントがローカル環境を壊しうる。** ファイルの改変・削除、
   環境変数や秘密情報の閲覧が、ユーザーと同じ権限で行われる
2. **隔離すると CLI に閉じこもる。** Docker や MicroVM に押し込めると、
   GUI の利点（ファイルの閲覧、差分、文書の編集）が失われる

shovel は「**エージェントの実行・ファイル編集・ツール実行だけをサンドボックスへ
追い出し、GUI はホストで軽く動かす**」という形でこれを解く。

そのうえで、**非エンジニアも使えること**を目標に置く。コードを編集する立場に
ない人が、AI と対話しながらコードや仕様を理解する。プロジェクトに関係なく
壁打ちする。そういう使い方を想定している。

## 設計の指針

議論を通じて繰り返し効いた原則を挙げる。迷ったときはここへ戻る。

### 1. 前提条件を最小化する

git が使えることを前提にしない。特定のエージェントを必須にしない。
ホストに git やターミナルを要求しない。特定のワークフローを強制しない。

想定する配布形態は **OSS 公開・不特定多数**。これは実際に公開するか否かではなく、
**使い方を強制しない**という設計原則の宣言である。

### 2. 保証できないものを保証と名乗らない

**中途半端な保証は無保証より悪い。**

「読み取り専用」は実装手段が無かったため、概念ごと廃止した。
中途半端に revert する案も、Read only とも言えず必ず回復するとも言えないため
捨てた（一度は「変更を見せて、戻す操作を提供する」という折衷案を作ったが、
これも原則1「特定のワークフローを強制しない」と衝突する用途があると分かり、
後に廃止した。decisions.md A-3-8）。

### 3. アプリが状態を独占しない

ユーザーがターミナルから `sbx` を触ることを妨げない。
**自動で消さない、自動で足さない。** 差分を見せて選ばせる。

### 4. 責務を混ぜない

設計が曖昧になったときは、たいてい別々のものを1つに数えていた。

- 「検知」→ ツリーの表示 / 開いているファイルの内容（2つ）
- 「認証」→ Docker / エージェント / ACP アダプタ（3レイヤー）

### 5. 作らずに済むものは作らない

IDE が無償で提供していたものを全部自作することになるため、範囲を絞る。

- コードを書くのは AI であって人間ではない → 重量級エディタは載せない
- フル機能のターミナルは組み込まない → OS のターミナルを借りる
  （TUI が要るコマンドは、PTY をサンドボックス内で作る TTY モードで動かす）
- **ネイティブモジュールをゼロにする** → 配布と署名が単純になる

### 6. 取り返しをつける

削除は `fs.rm` ではなく `shell.trashItem()`（OS のゴミ箱）。
編集の競合は上書きではなく競合コピー。
`git clean` は使わない。

## 用語

| 用語 | 意味 |
| :--- | :--- |
| **ACP** | Agent Client Protocol。エディタと AI エージェントの間の JSON-RPC 2.0 ベースの規格。stdio で通信する |
| **ACP アダプタ** | エージェントを ACP に対応させるラッパー。`npx` でサンドボックス内に入れる |
| **sbx** | Docker Sandboxes の CLI |
| **サンドボックス** | `sbx` が作る隔離環境。プロジェクトと1対1 |
| **ワークスペース** | サンドボックスにマウントされたホストのディレクトリ |
| **プロジェクト** | shovel の管理単位。ホストのディレクトリ＋サンドボックス＋表示名 |
| **セッション** | ACP の会話単位。タブと1対1 |
| **ターン** | プロンプト送信から `stopReason` までの1往復 |
| **トランスクリプト** | チャットの本文表示領域 |
